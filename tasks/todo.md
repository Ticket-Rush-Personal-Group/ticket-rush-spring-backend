## 延後

- **以場次結束時間取代「快取保存期限」** —— 目前的過期時間是自載入起算的固定期限,
  而正確的來源應該是場次的結束時間。schema 沒有那個欄位,為它新增 domain 欄位是
  Phase 1 排除的範圍蔓延。**已知的代價:銷售期若超過保存期限,場次會在銷售中變成「未開賣」**
  —— fail-closed 的停擺,不是資料錯誤。Phase 2 有場次狀態時處理

- **快取 TTL 的設定責任應移進應用** —— 目前由開賣的那一方(壓測腳本)負責,
  應用只能在對帳時警告。Phase 2 的管理介面把「開賣」變成應用內的動作後,
  TTL 應由應用自己保證,而不是靠警告

- **Redis 高可用(Sentinel / Cluster)** —— 第 8 支刻意不做:單節點足以呈現本層的併發特性,
  高可用是部署議題(Phase 4),混進來會讓本層的數據多出一個無關的變數。
  **Cluster 另有一個具體阻礙**:預扣的 Lua 腳本同時操作 `stock:*` 與 `purchased:*` 兩個 key,
  Cluster 要求同一支腳本的 key 落在同一個 slot —— 屆時必須改用 hash tag

- **訂單查詢端點** —— 第 3 層回 202 且不提供 `orderId`,客戶端只拿到冪等鍵。
  Phase 1 沒有查詢端點,所以那個鍵目前無處可用。**這是 202 這個決定尚未付清的代價**,
  Phase 2 補上以冪等鍵查詢訂單的端點

- **多實例部署時的 consumer name** —— 目前寫死 `consumer-1`。多實例共用同一個名稱會讓
  兩個實例共享 pending 清單、互相認領對方尚未處理完的訊息。部署前必須改為每實例唯一

- **重試退避(backoff)** —— 第 7 支刻意不做:重試風暴正是該層要量的現象,加退避會把它蓋掉。
  基準數據已取得(平均 7.04 次嘗試、最大 48 次、每張票伴隨約 13 次失敗嘗試)。
  **但第 7 支的上限對照顯示重試次數不是吞吐的瓶頸**(上限 100 與 10 的吞吐相同),
  因此退避能改善吞吐的機會不大 —— 若要做,目標應是延遲與資料庫負載,而不是吞吐

- **跨列鎖的順序** —— 目前只鎖單一庫存列,不會死鎖。若日後出現需要同時鎖多列的情境
  (例如跨場次套票),必須先定義鎖的取得順序,否則會死鎖

- **已取消訂單應排除於限購計算** —— 目前 `SUM(quantity)` 不篩選狀態。Phase 2 引入逾時取消後,
  已取消的訂單不應繼續佔用使用者的限購額度。現在只有 PENDING 狀態,該邏輯無法驗證,故不預先實作

- **Spring Security / 真實登入** —— Phase 2。橫切關注點,後加不需改架構;Phase 1 用 request header 帶 userId
- **訂單狀態機與逾時釋放庫存** —— Phase 2。逾時釋放是第三個併發考點(排程釋放與購買競爭同一列庫存)
- **Thymeleaf 管理介面** —— Phase 2,含策略即時切換與壓測儀表板
- **前台與 SSE 等候室** —— Phase 3,獨立 repo
