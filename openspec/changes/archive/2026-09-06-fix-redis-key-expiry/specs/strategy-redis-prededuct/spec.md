## ADDED Requirements

### Requirement: 快取 key 的生命週期

第 3 層寫入 Redis 的 key SHALL 有明確的過期時間。

`purchased:{eventId}:{userId}` 是**每個購買者一個 key** —— 沒有過期時間即為無界的記憶體成長。
這個缺陷不會使任何測試失敗、不會產生錯誤訊息、也不會出現在壓測中(環境每次重建),
因此 MUST 由本需求以測試守住。

**過期的順序:**

**`purchased` MUST 晚於 `stock` 過期。** 兩者的失敗方向不對等:

| 誰先過期 | 後果 |
| --- | --- |
| `stock` 先 | 場次視為「未開賣」,購票停止 —— **fail-closed,安全** |
| `purchased` 先 | 該使用者的限購額度歸零,可重新買一輪 —— **超買** |

**設為相同的到期時間 SHALL NOT 被視為滿足本條。** Redis 的過期是惰性 + 抽樣的:
key 不在到期瞬間消失,而是被存取時或被背景取樣掃到時才移除。
兩個到期時間相同的 key **完全可能出現「一個已消失、另一個還在」的窗口**,
而其中一半的可能性是不安全的那一半。

**繼承關係:**

`purchased` 的期限 MUST 繼承自 `stock` 的**絕對**到期時間再加上安全緩衝,
而非由呼叫端分別指定。分別指定等於把一條安全條件交給每一個呼叫端記得;
繼承讓它成為結構上必然成立的事。

`stock` 沒有過期時間時,`purchased` 也 SHALL NOT 設定 —— 保持一致,不走向不安全的方向。
該情況 MUST 產生警告(見下)。

**回補不得清除過期時間:**

回補路徑 MUST 使用保留 TTL 的操作(`INCRBY` / `DECRBY`),SHALL NOT 使用 `SET`。

**這一條守的不是本專案的邏輯,是本專案對 Redis 的假設。**
把回補改寫成「讀出來、算好、`SET` 回去」是一個看起來完全合理的重構,
而它會無聲地移除過期時間 —— 所有測試依然全綠。因此 MUST 有測試明確斷言
「回補之後過期時間仍然存在」。

**遺漏必須可見:**

未設定過期時間的 `stock` key MUST 產生警告。
檢查 SHALL 由既有的對帳掃描順便完成 —— 它本來就在列舉 `stock:*`。

**SHALL NOT 以拒絕預扣的方式處理遺漏** —— 那會把「慢慢洩漏」變成「完全不能賣票」,
用一個更嚴重的故障去防一個較輕的問題。**警告的責任是讓人知道,不是替人做決定。**

**已知的落差:**

過期時間代表的是「快取的保存期限」,**不是「場次的結束時間」**。
schema 中沒有後者,而為了過期時間新增 domain 欄位屬於 Phase 1 排除的範圍。

因此:**銷售期若超過保存期限,`stock` 會在銷售進行中過期,場次變成「未開賣」。**
那是 fail-closed 的停擺而非資料錯誤,但它是真實的限制,MUST 記錄於 spec 而非僅在註解中。
**SHALL NOT 以「把期限設成極大值」規避** —— 那是把問題藏起來,而且會讓它再也不被想起。

#### Scenario: 已購數的期限晚於庫存

- **WHEN** `stock` 帶有過期時間,且發生一次成功的預扣
- **THEN** `purchased` SHALL 具有過期時間
- **AND** 其到期時間 SHALL **晚於** `stock` 的到期時間,而非相同

#### Scenario: 庫存沒有過期時間時保持一致

- **WHEN** `stock` 沒有過期時間,且發生一次成功的預扣
- **THEN** `purchased` SHALL NOT 被設定過期時間 —— 一致,且不走向不安全的方向

#### Scenario: 回補後過期時間仍在

- **WHEN** 對一個帶有過期時間的 `stock` 執行回補
- **THEN** 該 key 的過期時間 SHALL 仍然存在
- **AND** 回補 SHALL NOT 以 `SET` 實作

#### Scenario: 缺少過期時間會被警告

- **WHEN** 對帳掃描到沒有過期時間的 `stock` key
- **THEN** SHALL 產生警告
- **AND** SHALL NOT 因此拒絕該場次的預扣

#### Scenario: 對帳不得憑空建立沒有過期時間的 key

- **WHEN** 某場次的 `stock` 已經過期而不存在
- **THEN** 對帳 SHALL 略過該場次,SHALL NOT 執行回補
- **AND** 理由是 `INCRBY` 對不存在的 key 會建立它**且新 key 沒有過期時間** ——
  那會憑空造出一個永不過期的 key
