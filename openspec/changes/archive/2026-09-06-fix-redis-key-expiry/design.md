## Context

第 8 支把庫存搬進 Redis,但**沒有任何一個 key 設過期時間**。實際確認過:`StockCacheAdapter`、
`pre-deduct.lua`、`restore.lua`、`k6/run-load-test.sh` 裡都沒有 `EXPIRE` / `TTL` 相關的呼叫。

受影響的兩組 key:

| key | 數量 | 生命週期 |
| --- | --- | --- |
| `stock:{eventId}` | 每場次一個 | 永遠 |
| `purchased:{eventId}:{userId}` | **每個買過票的人一個** | 永遠 |

後者是問題的主體:一場一萬人搶的活動留下一萬個 key,活動結束後它們仍在。

**這個缺陷有三個讓它特別容易被漏掉的性質:**

- **不會有任何測試變紅** —— 測試裡 key 少、生命週期短,行為完全正確
- **不會有錯誤訊息** —— Redis 只是慢慢長大,直到某天撞上 `maxmemory`
- **壓測也看不出來** —— 每次壓測都重建容器,key 從零開始

既有的相關決策(第 8 支)本支不推翻:Redis 是准入控制、資料庫是最終帳本;
應用刻意不提供「載入庫存」端點(D7),載入由開賣的那一方負責。

## Goals / Non-Goals

**Goals:**

- 兩組 key 都有明確的過期時間,且**過期順序不會造成超買**
- 忘記設定過期時間時**看得見**,而不是安靜地繼續洩漏
- 回補路徑不得把已設定的過期時間洗掉

**Non-Goals:**

- **不新增 `sales_end_at` 之類的 domain 欄位** —— 見 D2。為了 TTL 增加領域概念是範圍蔓延
- **不改變第 8 支的任何併發行為** —— 本支只碰生命週期,不碰預扣、落庫、補償、對帳的邏輯
- **不處理已經產生的孤兒 key** —— Phase 1 的環境每次重建。正式環境的一次性清理屬於部署議題

## Decisions

### D1. `purchased` 的期限繼承 `stock`,而且刻意多一段緩衝

腳本以 `EXPIRETIME` 讀出 `stock` 的**絕對**到期時間,再用 `EXPIREAT` 套到 `purchased`,並加上一段緩衝。

**為什麼是「繼承」而不是「各自設定」:** 讓呼叫端分別傳兩個期限,等於把一條安全條件交給每一個呼叫端記得。繼承讓它變成結構上必然成立的事。

**為什麼要緩衝 —— 這是本支最重要的一點。過期的順序決定安全與否:**

| 誰先過期 | 後果 |
| --- | --- |
| `stock` 先 | `stock` 不存在 → 場次視為「未開賣」→ 購票停止。**fail-closed,安全** |
| `purchased` 先 | 該使用者的限購額度歸零 → **可以重新買一輪。直接超買** |

**設成「相同時間」並不足夠。** Redis 的過期是**惰性 + 抽樣**的:key 不會在到期的瞬間消失,
而是在被存取時、或被背景取樣掃到時才移除。兩個到期時間相同的 key,
**完全可能出現「一個已經消失、另一個還在」的窗口** —— 而其中一半的可能性是不安全的那一半。

因此 `purchased` 的期限 = `stock` 的期限 + 緩衝,讓它**確定**活得比 `stock` 久。

**這個不對稱與對帳的「寧可漏補,不可誤補」是同一個原則**:兩種失敗方向的代價不對等時,
就往代價小的那邊偏。

**緩衝值以常數而非設定表達**:它是安全邊界,不是可調參數。做成設定只會讓某天有人把它調成 0。

**`stock` 沒有過期時間時,`purchased` 也不設** —— 保持兩者一致,不會走到不安全的方向。
這種情況由 D3 的警告負責讓人看見。

### D2. 過期時間是「快取保存期限」,不是「場次結束時間」—— 並且誠實標示這個落差

正確的來源應該是場次的結束時間。**但 schema 裡沒有這個欄位**,
而為了 TTL 新增一個 domain 欄位是 Phase 1 明確排除的範圍蔓延
(`openspec/project.md`:「任何無助於呈現併發策略差異的功能都不進 Phase 1」)。

**採用:自「載入快取庫存」起算的固定保存期限,由載入的那一方指定。**

**代價必須寫進 spec,不能只放在註解裡:** 若某場次的銷售期超過該期限,
`stock` 會在**銷售進行中**過期,場次變成「未開賣」,購票停止。

那是一次 **fail-closed 的停擺,不是資料錯誤** —— 方向是對的,但它是真實的限制。
Phase 2 有場次狀態與逾時機制時,應改為以場次的結束時間為準。

**不選「設一個大到不可能撞到的值(例如一年)」**:那等於把問題推遲而不是解決,
而且它會讓「TTL 到底該多長」這個問題再也不會被想起。

### D3. 忘記設定過期時間要被看見 —— 由對帳的排程順便檢查

TTL 由載入端設定,而載入端目前是壓測腳本(Phase 2 是管理介面)。
**忘記加上去的話,兩組 key 都不會過期,而且完全沒有徵兆。**

**對帳的排程本來就在掃 `stock:*`**(`eventsOnSale()`),讓它順便對「沒有過期時間的 stock key」
發出 WARN —— 零額外的掃描成本,把一個安靜的洩漏變成看得到的警告。

**不選「預扣時檢查並拒絕」**:那會讓忘記設 TTL 的後果從「慢慢洩漏」變成「完全不能賣票」,
用一個更嚴重的故障去防一個較輕的問題。**警告的責任是讓人知道,不是替人做決定。**

**不選「應用啟動時檢查」**:key 是動態產生的,啟動時檢查不到後來才載入的場次。

### D4. 回補不得洗掉過期時間 —— 而這件事要有測試釘住

`INCRBY` / `DECRBY` **會保留** key 既有的過期時間;只有 `SET` 會清除它。
本專案的回補路徑(`restore.lua`、`restoreStockOnly`)走的都是前者,因此目前是安全的。

**但這是我們依賴的一個 Redis 行為,不是自己寫的邏輯。** 哪天有人把回補改成
「讀出來、算好、`SET` 回去」—— 一個看起來完全合理的重構 —— 洩漏就無聲地回來了,
而且所有測試依然全綠。

因此要有測試明確斷言:**回補之後,`stock` 的過期時間仍然存在**。
這條測試守的不是我們的程式碼,是我們對 Redis 的假設。

### D5. 對帳在快取過期後不再涵蓋該場次 —— 這是可接受的

`eventsOnSale()` 掃不到已過期的 key,該場次因此離開對帳範圍。

**這不影響正確性:** 訂單照樣會落庫(消費者不需要 Redis 庫存),
消失的只是快取的帳 —— 而場次都下架了,那本帳也沒有意義。

前提是**過期時間遠長於落庫的收斂時間**。第 8 支實測收斂 ≤ 200ms,而保存期限以小時計,
兩者差了五個數量級。

**一個必須避免的反模式:** 對帳的回補走 `INCRBY`,而 **`INCRBY` 對不存在的 key 會建立它,
且新 key 沒有過期時間** —— 那會憑空造出一個永不過期的 key,把剛修好的洩漏帶回來。
目前不會發生(`available()` 為空時對帳直接略過),但這個順序依賴必須寫下來。

## Risks / Trade-offs

- **[保存期限短於實際銷售期 → 銷售中斷]** → D2 已說明。fail-closed,方向正確,且可設定。
  **不得為了避免這個風險而把期限設成極大值** —— 那是把問題藏起來
- **[TTL 由應用外部設定,應用無法保證它存在]** → D3 的警告是唯一的防線,而警告會被忽略。
  真正的解法是 Phase 2 把「開賣」變成應用內的動作,屆時 TTL 由應用自己負責
- **[緩衝值 1 小時是拍腦袋的]** → 它只需要「大於 Redis 惰性過期的不確定性」,
  而那是秒等級。一小時有五個數量級的餘裕,不需要調校
- **[對帳每輪多一次 TTL 查詢]** → Phase 1 只有一個場次,可忽略。
  場次數量成長後應改為只在首次發現時警告一次

## Migration Plan

**無 schema 變更,無相依變更。**

**行為變更僅一項:** 新載入的 `stock` key 會帶有過期時間,而 `purchased` 會繼承它。
既有(已在 Redis 中)的 key 不受影響 —— 本支不處理已產生的孤兒 key,
Phase 1 的環境每次重建。
