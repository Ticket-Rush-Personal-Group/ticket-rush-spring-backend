## Why

第 15 支留下兩個問題,而它們是同一件事的兩面:

1. **無序列化點時,虛擬執行緒為何仍快 10.8%～13.9%?**
   准入併發度**已被排除** —— 平台在 200 與 1000 兩個上限下輸給虛擬的幅度相同
2. **`P1000` 比 `P200` 慢的 5.4%,有多少來自排隊、多少來自執行緒本身?**
   而在平台模型上,**准入 N 個請求就必然要 N 條執行緒 —— 兩個旋鈕物理上是同一個**,
   靠調 Tomcat 參數分不開

**兩者都指向同一個未知數:一條平台執行緒比一條虛擬執行緒多付了什麼?**

而目前為止所有數據都只有吞吐。**吞吐是結果,不是機制** ——
兩個組態可以有相同的吞吐而 CPU 差一倍,也可以有相同的 CPU 而吞吐差一倍,
**那兩種情況指向完全相反的結論,在吞吐數字上卻長得一模一樣。**

cgroup v2 的 `cpu.stat` 已經提供了需要的一切,不需要 Micrometer:
累計 CPU 時間、**user / system 拆分**、以及被 CPU 配額節流的次數。
**執行緒的切換與排程是核心的工作 —— 假說預測的具體現象是 system 時間/請求偏高**,
那是可證偽的,而「CPU 比較多」不是。

**怎樣算做完:**

1. 每組量到「每請求的 CPU 時間」與其中的 user / system 拆分,應用與資料庫兩邊都有
2. 對兩個問題各自依**事先寫下的判準**給出答案 —— 包含「本探針答不出來」
3. 量測期間若撞到 CPU 配額,看得出來且該批不得用於比較

## What Changes

- `k6/run-load-test.sh`:量測前後讀 app 與 postgres 容器的 cgroup `cpu.stat`,
  輸出每請求 CPU 時間、user / system 拆分、平均使用率與節流次數
- **讀累計計數器而非 `docker stats` 的瞬時值** —— 量測窗口只有約 20 秒,
  抽樣器本身會跟被測系統搶 CPU,而那正是本支要量的東西
- `k6/run-comparison-matrix.sh`:CPU 欄位收進逐組輸出與 TSV
- 以第 15 支的六組(`P200` / `P1000` / `V` × `pessimistic` / `noLock`)重跑並判定

## Capabilities

### Modified Capabilities

- `platform-load-test-environment`:新增一條需求「效能結論若涉及成本歸因,
  必須有吞吐以外的量測」—— 吞吐是結果不是機制;並要求 CPU 配額的節流狀況
  必須被記錄且能否決比較。

## Impact

**不改動應用程式碼,無 schema 變更,不改動任何量測參數。**
組別、輪數、暖機協定、排程演算法全部沿用第 15、16 支。

**不新增組別。** 先看 CPU 訊號再決定 —— 若指向「執行緒本身的成本」,
`-Xss` 對照才有意義;若指向「請求在等」,它完全無關。
**現在排進去等於在賭一個還沒問的問題的答案。**

**需要使用者手動執行:** 六組 × 三輪約 25 分鐘。機器須接上電源全程不得拔除,
OrbStack 不得關閉。
