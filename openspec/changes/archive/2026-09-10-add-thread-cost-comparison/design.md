## Context

第 15 支留下兩個問題,而它們是同一件事的兩面。

**問題一(候補①):無序列化點時,虛擬執行緒為何仍快 10.8%～13.9%?**

第 15 支已經**排除了准入併發度**:平台在 200 與 1000 兩個准入上限下,
都輸給虛擬同樣的幅度(10.8% / 13.9%)。**那個差異與「同時放進來幾個」無關。**

**問題二(候補②):`P1000` 比 `P200` 慢的 5.4%,有多少來自排隊、多少來自執行緒本身?**

第 15 支寫下這個干擾因素時,我還沒想清楚一件事:
**在平台模型上,准入 N 個請求就必然要 N 條執行緒 —— 這兩個旋鈕物理上是同一個。**
想靠調 Tomcat 參數把它們分開是做不到的。

**兩個問題都指向同一個未知數:一條平台執行緒比一條虛擬執行緒多付了什麼?**

而目前為止的所有數據都只有吞吐 —— **吞吐是結果,不是機制。**
兩個組態可以有相同的吞吐而 CPU 用量差一倍,也可以有相同的 CPU 而吞吐差一倍,
**那兩種情況指向完全不同的結論,但在吞吐數字上長得一模一樣。**

## Goals / Non-Goals

**Goals:**

- 取得**機制層面**的量測,而不只是吞吐:每個請求花掉多少 CPU,其中多少是核心的工作
- 對兩個問題各自給出**事先寫下判準**的答案
- 環境若被 CPU 上限限制,要看得出來 —— 那會讓整個比較失去意義

**Non-Goals:**

- **不改動應用程式碼、不改動 schema、不改動任何量測參數**
- **不新增組別** —— 見 D5。先看訊號,再決定要不要加
- **不做 `-Xss` 對照** —— 見 D5,那是有條件的後續,不是本支的內容
- **不引入 Micrometer / Prometheus** —— 那是 Phase 4。本支要的東西 cgroup 就有

## Decisions

### D1. 量 cgroup 的**累計** CPU 時間,不量 `docker stats` 的瞬時百分比

量測窗口只有約 20 秒,而 `docker stats` 給的是抽樣後的瞬時速率 ——
要用它就得在跑的期間持續抽樣,而**抽樣器本身會跟被測系統搶 CPU**,
那正是本支要量的東西。

cgroup v2 的 `cpu.stat` 是**單調遞增的累計計數器**,前後各讀一次相減即為精確總量,
沒有抽樣誤差,也不需要在量測期間跑任何額外的東西。

```
usage_usec   累計 CPU 時間
user_usec    使用者態
system_usec  核心態
nr_throttled 被 CPU 配額節流的次數
```

### D2. **拆 user / system,那才是判別的關鍵**

單一個「CPU 用了多少」無法區分「應用做了更多事」與「核心花了更多力氣調度」。

**執行緒的建立、切換與排程是核心的工作,落在 system 時間。**
「一條平台執行緒比虛擬執行緒多付了什麼」這個假說,
預測的具體現象是 **system 時間/請求偏高** —— 那是一個可證偽的預測,
而「CPU 比較多」不是。

### D3. **同時量應用與資料庫兩個容器**

只量應用會漏掉關鍵的一種情況:**請求在資料庫那邊排隊時,應用是閒著的。**

兩邊都量,才分得出:

- 應用 CPU/請求相當、資料庫 CPU/請求相當、但吞吐較低 → **請求在等**
- 應用 system 時間/請求較高 → **執行緒本身的成本**

### D4. 一併記錄 `nr_throttled`,而且它能否決比較

容器有 `cpus: 4` 的配額。若量測期間撞到配額,吞吐是被**上限**決定的,
不是被執行緒模型決定的 —— **而那會安靜地讓整個比較失去意義**,
症狀只是「數字比預期低」。

與記憶體守則同一個道理:**條件表上要有它,而且它要能說「這批不算」。**

### D5. **不新增組別,先看訊號**

沿用第 15 支的六組(`P200` / `P1000` / `V` × `pessimistic` / `noLock`),
只加探針。

**理由是「先量再決定」而不是「一次做完」:**
若 CPU 數據指向「執行緒本身的成本」,`-Xss` 對照才有意義(降低堆疊,看成本是否來自記憶體);
若指向「請求在等」,`-Xss` 完全無關 —— **現在就排進去等於在賭一個還沒問的問題的答案。**

第 15 支的 D6 是同一個判斷:判別力來自對的探針,不是來自組數。

**`-Xss` 對照是有條件的後續,不是被忘記。** 判定若指向執行緒成本,收尾時進 todo。

### D6. 兩個問題的判準,事先寫下

**問題一 —— noLock 層,虛擬 vs 平台:**

| 觀察 | 結論 |
| --- | --- |
| V 的 **system 時間/請求明顯較低** | 虛擬省下的是**核心層的執行緒成本**,問題一得解 |
| 兩者 CPU/請求相當,但 P 未觸及 CPU 上限而吞吐較低 | 平台不是被 CPU 限制,而是被**並行度**限制 |
| 兩者 CPU/請求相當且**都觸及 CPU 上限** | 差異來自別處,**本探針答不出來** —— 如實說 |

**問題二 —— pessimistic 層,P1000 vs P200:**

| 觀察 | 結論 |
| --- | --- |
| CPU/請求相當(應用與資料庫皆是),吞吐較低 | 請求在**等** —— 放寬准入的代價是排隊 |
| **system 時間/請求較高** | **執行緒本身的成本**,不是排隊 |
| 兩者皆有 | 部分各半,**必須說清楚各佔多少,不得只報其一** |

**三種結果對兩個問題都算成功。** 包括「本探針答不出來」——
那也是結論,而且它會指出下一步該量什麼。

## Risks / Trade-offs

- **[讀 cgroup 需要 `docker exec`,前後各一次]** → 在 k6 執行的**外面**,不進入量測窗口。
  兩次 exec 的成本對所有組別相同
- **[使用率的分母是牆鐘秒,解析度只有 1 秒]** → macOS 的 `date` 沒有次秒精度。
  **CPU/請求不受影響**(它的分母是請求數),只有「使用率」這個輔助指標會有數 % 的誤差,
  報告時標明
- **[括號涵蓋 k6 執行 + 非同步落庫收斂]** → 對 `pessimistic` / `noLock` 而言收斂是空操作。
  Redis 預扣層若日後要量,那段落庫的 CPU 本來就該算進去
- **[六組的數據是新取得的,不能與第 15 支的數字混用]** → 本來就不該混用。
  本支的判定一律在**本批之內**進行

## Migration Plan

**不改動應用程式碼,無 schema 變更,無相依變更,不改任何量測參數。**

- `k6/run-load-test.sh`:量測前後讀 cgroup,輸出 CPU 摘要行
- `k6/run-comparison-matrix.sh`:把 CPU 欄位收進逐組輸出與 TSV

組別、輪數、暖機協定、排程演算法全部沿用。
