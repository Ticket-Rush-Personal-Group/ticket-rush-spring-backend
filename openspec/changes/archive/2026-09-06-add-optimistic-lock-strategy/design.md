## Context

第 6 支交出了第一個正確的實作:悲觀鎖零超賣、零超買,吞吐相對第 0 層只降 16%。本支要回答的是另一個方向的問題 —— **不鎖,靠偵測衝突後重試,能不能也達到正確,代價又是什麼。**

探索既有程式碼時發現,樂觀鎖的落點在前幾支已經預先鋪好,而且都留下了明確的但書:

- `stock.version` 欄位在第 2 支的 `V1__init_schema.sql` 就建立了,註解寫明「樂觀鎖使用(第 7 支)。現在納入是因為它是已定案的需求,不是預留彈性」
- `StockJpaEntity` 的 `version` **刻意沒有標 `@Version`**,註解寫明「標註後 Hibernate 會對每一次 update 都執行樂觀鎖檢查,那會改變第 0 層與第 1 層的行為」,並把「交給 Hibernate 還是條件式 UPDATE」留給本支決定
- `Stock` domain model 的 `deduct` 不變動 `version`,註解寫明「版本號的遞增由持久化層負責」
- `LoadStockPort` 的 javadoc 已經預告本支要新增的 port 叫 `CompareAndDeductStockPort`(回傳影響列數)
- `purchase_order.idempotency_key` 的註解寫明「在有重試機制的系統中這是必要條件而非加分項:**樂觀鎖策略必然重試**」

四層策略置於 in port、各策略持有自己的交易邊界、port 跟著策略進來等既有決策見 `openspec/project/backend-architecture.md`。

**本支與第 6 支的關鍵差異:悲觀鎖有一把排他鎖可以把所有檢查藏在後面,樂觀鎖沒有。** 第 6 支 D1 的「鎖前快篩 + 鎖後權威檢查」在這裡無法照搬 —— 版本號只保護 `stock` 那一列,限購讀的是 `purchase_order` 的聚合。正確性因此改由**讀取順序**與**每次嘗試都是獨立交易**這兩件事共同支撐,兩者都沒有任何編譯期或框架層的保護。

## Goals / Non-Goals

**Goals:**

- 樂觀鎖策略,零超賣且零超買
- 解決「版本號保護不到限購聚合」的衝突,且說明它為什麼成立
- 取得**重試次數分佈**(不只平均值)與重試耗盡率 —— 本層 spec 規定的特有量測項目
- 以「重試上限 100 vs 10」的對照量化重試風暴的代價
- 與第 1 層(悲觀鎖)在相同條件下的效能對照

**Non-Goals:**

- **不修改第 0、1 層** —— 四層必須並存才能比較
- **不加退避(backoff)** —— 見 D6。重試風暴正是本層要量的現象
- **不採用 Hibernate 的 `@Version`** —— 見 D1。它會改變其他三層的行為
- **不追求本層的效能最佳化** —— 與第 6 支同樣的理由:調快它會模糊四層的區別
- **不處理 ABA** —— 版本號單調遞增且只在此一處遞增,不會回頭

## Decisions

### D1. 以條件式 UPDATE 自行控制版本,不用 Hibernate 的 `@Version`

```sql
UPDATE stock SET available = ?, version = version + 1
 WHERE event_id = ? AND version = ?
```

回傳影響列數:`1` 代表 CAS 成功,`0` 代表版本已被他人推進。

**不選 `@Version`(第一個、也是決定性的理由):它不是只影響本層。** Hibernate 的樂觀鎖檢查會套用在**所有**對 `StockJpaEntity` 的 update 上,而第 0 層與第 1 層都走同一個 `repository.save()`。標上去之後,第 0 層的超賣會被 Hibernate 擋掉一部分,第 1 層的行為也跟著變 —— **四層就不再是同一個基準,而本專案的核心產出正是四層比較。** `StockJpaEntity` 的既有註解已經預先指出這件事,本支只是執行它。

**不選 `@Version`(第二個理由):它用例外做流程控制。** 失敗時拋 `OptimisticLockingFailureException`,重試迴圈得靠 catch 驅動。條件式 UPDATE 回傳 0 是一個普通的回傳值,重試讀起來就是一般的控制流程 —— 而重試次數的統計也只是迴圈裡的一個計數器,不必從框架內部挖。

**代價**:`available` 的絕對值由呼叫端算好後寫入(與 `UpdateStockPort` 一致),因此 CAS 的正確性完全依賴版本條件,而不是 `available = available - ?` 這種資料庫端運算。這是刻意的 —— 資料庫端運算會讓列鎖天然序列化,那是第 0 層的 `UpdateStockPort` 註解已經否決過的寫法,理由相同:它會讓策略之間的差異消失。

### D2. CAS 的條件只放版本,可用量的檢查留在 domain

`WHERE event_id = ? AND version = ?`,**不加** `AND available >= ?`。

**不選把可用量條件塞進 WHERE:那會讓 `0 rows` 有兩種意義** —— 版本衝突,或庫存不足。而這兩者要的處置完全相反:

| 情況 | 正確處置 |
| --- | --- |
| 版本衝突 | **重試** —— 對手改了庫存,重讀後我可能還買得到 |
| 庫存不足 | **立即拒絕** —— 重試一百次也不會變出票來 |

無法區分就無法決定,而選錯的代價很具體:售罄之後的 500 個請求會各自重試到上限才放棄,把重試風暴放大一個數量級,量到的分佈也不再反映真實的競爭。

因此:庫存不足由 `Stock.deduct` 拋 `InsufficientStockException`(既有的 domain 規則,已有單元測試涵蓋),CAS 的 `0 rows` 唯一的意義就是版本衝突。**領域規則留在 domain,不搬進 SQL。**

資料庫的 `ck_stock_available_non_negative` 仍在,作為基礎設施的第二道防線 —— 但它不是本層的正確性依據。

### D3. 重試迴圈必須在交易之外,而且不能靠自我呼叫

**這是本支最容易寫錯的地方,而且錯了不會有任何錯誤訊息。**

每一次嘗試必須是一個**獨立且已提交**的交易。理由是因果的:CAS 回傳 0 意味著對手的交易已經提交(PostgreSQL 的 UPDATE 會先阻塞在對手持有的列鎖上,等它提交後才重新評估 WHERE)。重試要有意義,就必須讀得到對手的那次提交。

**不選「整個重試迴圈包在一個 `@Transactional` 裡」:** READ COMMITTED 下每個語句取新快照,重讀確實看得到已提交的資料,所以正確性勉強成立 —— 但**連線在整個重試期間被佔用**。1000 併發、連線池 50,重試風暴會直接把連線池吃乾,量到的又會是「等連線」而不是「重試」。第 6 支 D4 已經證明這兩者在延遲圖表上分不出來,本支不能重蹈。

**不選「同一個類別裡把單次嘗試抽成 `@Transactional` 私有方法」:self-invocation 繞過 AOP proxy,交易根本不會生效。** 這正是 CLAUDE.md 列為「**無測試能抓到**」的 Hard Rule 之一。它的症狀特別惡劣:重試看起來在跑、數據看起來合理,實際上每次嘗試都不在自己的交易裡 —— 而這件事只會在併發下顯現。

**採用的結構:**

```
OptimisticPurchaseService     不標 @Transactional，持有重試迴圈與計數
        │  (跨 bean 呼叫，經過 proxy)
        ▼
OptimisticPurchaseAttempt     標 @Transactional，單次嘗試，成功回傳結果 / 衝突回傳空
```

兩個 bean 之間是正常的依賴注入呼叫,proxy 一定生效。

**不選 Spring Retry 的 `@Retryable`**:要新增相依,而且重試次數會落在框架內部,本層的頭號產出(重試次數分佈)反而更難取得。手寫迴圈只有十幾行,還能順手記錄每次嘗試。

### D4. 讀取順序決定正確性:先讀版本,再讀已購數

版本號只保護 `stock` 那一列。限購檢查讀的是 `purchase_order` 的聚合 —— **不在版本的保護範圍內**。這與第 6 支 D1 是同一個衝突,但那時可以躲在排他鎖後面,這裡沒有鎖可躲。

安全性的條件是:**已購數的讀取,必須涵蓋「版本讀取當下已提交的一切」。** 兩種順序的結果完全不同:

```
先讀版本 v、再讀已購數：
  對手在兩次讀取之間提交 → 已購數讀得到它（偏保守），而 CAS(v) 必定失敗 → 重試。安全。
  對手在兩次讀取之後提交 → CAS(v) 必定失敗 → 重試。安全。

先讀已購數、再讀版本：
  對手在兩次讀取之間提交 → 已購數是舊的、版本是新的 → CAS 成功 → 超買。
```

**所以順序是正確性的一部分,不是風格問題。** 兩個版本的程式碼長得幾乎一樣,而其中一個是錯的。

至於為什麼這樣就夠:CAS 讓該場次的所有成交**序列化**(同一時間只有一個交易能把版本推進一格)。限購檢查只要與成功的那次 CAS 位於同一個交易、且讀取順序正確,讀到的已購數就精確反映了「在我之前成功的所有人」。

**反向驗證:把兩次讀取對調,併發限購測試必須變紅。** 這個競態的窗口很窄,若對調後仍為綠,就在對調版本的兩次讀取之間插入短暫 sleep 把窗口撐開再驗 —— **撐開窗口是為了讓既有的競態顯現,不是製造一個不存在的競態**,證完即還原。改不紅的反向驗證等於沒有驗證(第 1、2 支的 lessons 已經踩過兩次)。

### D5. 重試上限 100,另跑一組上限 10 的對照

上限可設定(`ticket-rush.optimistic.max-attempts`),否則壓測要改程式碼才能對照。

**驗收用 100 的理由:** 1000 併發搶 500 張是極端競爭,上限太低會讓請求**重試耗盡**而失敗,售出就 < 500。那不是超賣 —— 是本層特有的**另一種**失敗模式,但它會讓「售出恰好 500」的驗收無法成立。第 6 支已經定調斷言必須用「恰好」而非「不超過」,因為後者在系統完全停擺時也會通過。要保住這個力道,驗收就得在重試足夠的前提下進行。

**上限 10 的對照組要回答:低上限是犧牲成交率換吞吐,還是兩者都輸?** 手法沿用第 6 支的連線池對照 —— 其餘條件完全不變,只改一個變數。那是第 6 支最有價值的產出,理由是它給的是實驗結果而不是推斷。

**若驗收在上限 100 下仍出現重試耗盡**,照實記錄並提高上限,**不得把斷言改成「不超過」** —— 那等於默默放棄本層的正確性驗收。

### D6. 不加退避(backoff)

**重試風暴正是本層要量的現象,加退避等於把它蓋掉。**

退避幾乎確定會讓數字變好看,但它改善的是一個**還沒被量化的問題**。先量出立即重試的基準,再談要不要治 —— 否則本層交出的會是「加了退避的樂觀鎖」的數據,而不是樂觀鎖的數據,四層比較就少了一格。

退避記入 `tasks/todo.md` 延後,條件是「基準數據出來後,若重試風暴確實是主要成本」。

### D7. 重試次數分佈以行程內直方圖收集,關閉時輸出

`strategy-*` 的慣例規定本層的特有量測項目是「重試次數分佈(**不只平均值**)」。平均值會把「多數請求一次成功、少數重試五十次」和「所有請求都重試三次」畫成同一個數字,而這兩者是完全不同的系統。

`RetryStatistics`:以 `AtomicLongArray` 依嘗試次數計數,另計重試耗盡數,於 `ContextClosedEvent` 輸出一行摘要。

**不選「回應標頭帶 `X-Retry-Count`」**:汙染正式 API。`k6/run-load-test.sh` 的既有註解已經定調 ——「刻意不為此在應用加測試專用端點,那會污染正式 API」,標頭是同一件事的變形。

**不選「每個請求記一行 log」**:1000 併發下的 log I/O 會影響**被量測的數字本身**。觀測手段不該改變被觀測的對象,而這是壓測裡最常見的自我汙染。

**不選 Micrometer**:觀測方案(Micrometer / Prometheus / Grafana)是 Phase 4 的事,現在拉進來等於提前替 Phase 4 決定,而且為了一個計數器引入整套 registry 不成比例。

**這個做法沿用既有模式:** `RuntimeInfoLogger` 已經確立「讓被測系統自己報告它的實際狀態」—— 那是第 4 支從「compose 設定被靜默替換」學到的。本元件是同一個原則在關閉端的對應。

### D8. 新增錯誤碼 `RETRY_EXHAUSTED`,對應 409

`ErrorCode` 的既有規定:「新增錯誤情境時,碼名 MUST 先於實作在 spec 中定名」,故在此定名。

- `RETRY_EXHAUSTED` → HTTP 409,訊息不得洩漏重試次數等內部細節
- **不併入 `INSUFFICIENT_STOCK`**:兩者的意義完全不同。庫存不足是「沒票了」,重試耗盡是「有票但你搶輸了太多次」—— 客戶端對後者的合理反應是重送,對前者則不是。碼名描述發生了什麼事,這是 `ErrorCode` 既有的規定。
- **重試耗盡在壓測中的比例是本層的產出之一**,而不是要被消除的雜訊。

## Risks / Trade-offs

- **[重試耗盡不是超賣,但它是本層特有的失敗模式]** → 驗收條件必須明確區分兩者:零超賣是必須,重試耗盡率是要被量測與解讀的數字。**不得因為耗盡率難看就調高上限重跑當作基準** —— 上限本身就是測量條件的一部分。
- **[D4 的反向驗證窗口極窄,可能不穩定]** → 已在 D4 訂出處置:對調後若仍綠,插入短暫 sleep 撐開窗口再驗,證完還原。**若撐開後仍不紅,代表 D4 的推理有誤,必須回頭重新檢視,不得跳過。**
- **[本層吞吐可能比悲觀鎖差]** → 高競爭下樂觀鎖劣於悲觀鎖是合理的預期。**照實記錄並解讀,不修飾。** 樂觀鎖的優勢在低競爭場景,而搶票正是它最不擅長的形狀 —— 這個結論本身就是有價值的產出。
- **[CAS 寫入絕對值而非增量]** → 與 `UpdateStockPort` 同樣的設計。正確性完全依賴版本條件,少了版本條件就退化成第 0 層。ArchUnit 抓不到這個,靠 D4 的併發測試守住。

## Migration Plan

**無 schema 變更。** `stock.version` 在第 2 支的 `V1__init_schema.sql` 已建立,且當時就註明是為本支準備。CLAUDE.md 的 Hard Rule 禁止修改已套用的 migration,本支也不需要。

新增策略不影響既有的第 0、1 層 —— 新的 port、新的 service、新的錯誤碼都是**新增**,既有檔案只動 `ErrorCode`(加一個列舉值)、`GlobalExceptionHandler`(加一個 handler)與 `application.yml`(加一組設定)。
