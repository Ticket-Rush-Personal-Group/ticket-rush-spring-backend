## Context

第 13 支的交錯矩陣**整批作廢**:三輪水位 4622 → 4082 → 3759 req/s,漂移 **21.2%**(門檻 15%)。
八組中四組單調下降,水位本身也單調下降 —— 依第 11 支的教訓,**單調就代表有東西在累積**。

根因已追到底:

**`pg_multixact` 在批次期間累積到 679MB,佔掉 postgres 容器 1GB 上限的 68%。**

1. `V1__init_schema.sql:33` —— `purchase_order.event_id BIGINT NOT NULL REFERENCES event (id)`。
   每一筆 insert 都要對**同一個** `event` 列做外鍵檢查,取 `FOR KEY SHARE` 鎖
2. 1000 個併發請求同時持有那一列的共享鎖 → PostgreSQL 必須配置 **MultiXactId**
   來記錄「哪些交易同時鎖著這一列」
3. 24 次量測 × 50000 個請求 = **120 萬筆 insert,全部指向同一個父列**
4. 四個資料庫的 `datminmxid` 全部仍為 **1** —— `pg_multixact` **從未被截斷過**
5. 資料目錄在 **tmpfs(記憶體)**,那 679MB 直接算進容器的 `mem_limit: 1g` → 容器 **91.29%**
6. 整批最後一筆量測(`V_noLock`,t=2342s)崩到 **1084 req/s**,同組前兩輪為 4864 / 4665

**實測對照:**

| 做法 | `pg_multixact` | 容器記憶體 |
| --- | --- | --- |
| 批次結束時 | 679M | 91.29% |
| `VACUUM (FREEZE)` 三張表 + `CHECKPOINT` | 679M(沒動) | 91.29% |
| 重建 postgres-perf 容器 | **16K** | **17.95%** |

`VACUUM FREEZE` 讓 `event.relminmxid` 前進了(2999734 → 3049724),但 `datminmxid` 仍為 1 ——
**截斷看的是整個 cluster 的最小值**,而 `template0` 的 `datallowconn=false`,正常手段碰不到它。
**在單一容器的生命週期內,這個累積清不掉。**

**為什麼第 11 支沒發現:** 那批只有 8 次量測,第 13 支是 24 次 —— 三倍的寫入量。
而第 11 支加的 `CHECKPOINT` 修的是 **WAL**(第 13 支的 `pg_wal` 只有 64M,完全正常),
是另一個機制。**`TRUNCATE` 清不掉、`CHECKPOINT` 清不掉、`VACUUM FREEZE` 也清不掉。**

## Goals / Non-Goals

**Goals:**

- 讓量測環境**在整個批次期間維持同一個狀態** —— 這是「可比較」的前提
- 環境若仍然退化,要**大聲失敗而不是安靜地產生偏低的數字**
- 取得一批乾淨的交錯數據,回答第 13 支沒能回答的核心問題

**Non-Goals:**

- **不改動 schema,外鍵留著。** 見 D3 —— 那個外鍵不是 bug
- **不改動任何量測參數**:請求數、庫存、暖機協定、連線池、資源限制全部維持不變
- **不改動任何應用程式碼**
- **不改動 `run-comparison-matrix.sh` 的順序邏輯** —— 交錯與旋轉是第 13 支驗證過的,本支不碰

## Decisions

### D1. 每組連同 `postgres-perf` 一起重建,而不是想辦法清掉 multixact

矩陣目前每組重建 `app`:

```
docker compose --profile perf up -d --force-recreate --wait app
```

改為連 `postgres-perf` 一起:

```
docker compose --profile perf up -d --force-recreate --wait postgres-perf app
```

`depends_on` 已設 `condition: service_healthy`,compose 會先起 postgres 再起 app,
Flyway 於 app 啟動時對全新的資料庫跑 migration。**tmpfs 隨容器消滅,狀態保證乾淨。**

**為什麼不清而是重建:** 上表已經證明清不掉。`VACUUM FREEZE` 動不了 `datminmxid`,
而要動它得對每個資料庫做全庫 vacuum —— 包含 `datallowconn=false` 的 `template0`。
**能做到,但那是為了迴避一個「重建容器」就解決的問題而去改 cluster 的狀態**,
而且每一步都是新的隱藏變數。

**代價:** 每組多一次 postgres 冷啟動。實測約 8 秒,24 組共約 3 分鐘,
相對於 45 分鐘的批次是 7%。**而每組的「暖到收斂」協定會吸收掉冷快取的影響** ——
那個協定本來就是為了「重啟後從零開始」而設計的。

**不重建 `redis-perf`:** 第 13 支結束時它只用了 12.79MB / 1GB(1.25%),
且 `reset_data()` 已經逐輪清掉 `stock:*`、`purchased:*` 與 stream。**沒有證據顯示它會累積。**
不為「以防萬一」多付一次重建 —— 那會多一個沒有根據的變數。

### D2. 加一條**通用**的環境健康守則,而不是針對 multixact 的檢查

在 `run-load-test.sh` 正式量測開始前,檢查 postgres 容器的記憶體用量;
超過上限的一定比例(預設 **50%**)即**中止並說明**,不產出數字。

**為什麼是容器記憶體而不是 `pg_multixact` 的大小:**

multixact 是**這一次**找到的累積物。第 11 支找到的是 WAL,這次是 multixact ——
**兩次都是「量到單調下降之後回頭找」才發現的**。針對 multixact 寫檢查,
只能擋住已經知道的那一個;而容器記憶體是這些累積物**共同的出口**,
tmpfs、shared_buffers、WAL、multixact 全部算在同一個數字裡。

**判準的分離度是實測來的:** 乾淨時 17.95%,退化時 91.29%。50% 落在中間,
兩邊都有兩倍以上的餘裕。`pg_multixact` 的大小仍然印出來,但**作為診斷資訊而非判準**。

**這條守則必須能失敗。** D1 修好之後它應該永遠不觸發 —— 但「永遠不觸發」和
「根本沒有作用」在輸出上長得一模一樣,因此塊 2 要反向驗證它會在該紅的時候紅。

### D3. 外鍵留著 —— 它不是 bug,而且它本身就是本專案該講的東西

最直接讓 multixact 消失的做法是拿掉 `purchase_order.event_id` 的外鍵約束,
或讓它指向一個不競爭的列。**不做。**

理由有兩層:

**① 那會改變被量測的系統。** 四層策略的比較前提是「除了鎖策略以外一切相同」,
而外鍵檢查是每一層都要付的成本。拿掉它,量到的就不再是這個應用。

**② 這個現象本身是一個真實的可擴展性陷阱,值得留在交付物裡。**
「高頻插入的子表,外鍵指向一個熱點父列」在真實系統裡會產生大量 MultiXactId,
而它的症狀是**逐漸變慢**,不是報錯 —— 沒有任何測試會紅,監控上也只是「資料庫好像有點慢」。
本專案是學習專案,**這種只在夠大的量下才顯現、且無聲的現象,正是它該記錄的東西。**

因此:修的是**量測環境**(每組從乾淨狀態開始),不是修應用。
而這個發現會寫進 README 的素材。

### D4. 反向驗證:先證明守則會紅,再證明修正讓它不紅

順序不能顛倒。若先修好再加守則,守則從頭到尾都是綠的,**而那與「守則沒作用」無法區分**。

1. 在**尚未套用 D1** 的狀態下,連續跑幾組把 postgres 容器的記憶體推上去,
   確認 D2 的守則會中止並印出當時的數字
2. 套用 D1,確認同樣的組數跑完之後 `pg_multixact` 維持在 KB 等級、守則不觸發

### D5. 修完之後漂移若仍 > 15%,**不得調整門檻**

事先寫下來,避免結果出來之後才決定什麼算成功:

| 結果 | 處置 |
| --- | --- |
| 漂移 < 15%,`pg_multixact` 維持小 | 修正有效,**取得數據並回答第 13 支的核心問題** |
| 漂移 < 15% 但 `pg_multixact` 仍大 | multixact **不是**主因,本支的歸因有誤,回頭重查 |
| 漂移仍 > 15% | **還有第二個累積物。** 記錄容器記憶體與各目錄大小,再開一支 |

**門檻是 15%,不論結果如何都不動它。** 第 13 支訂它的理由沒有因為這次失敗而改變 ——
**改門檻就等於讓驗收去遷就數據。**

## Risks / Trade-offs

- **[每組多一次 postgres 冷啟動]** → 約 8 秒 × 24 = 3 分鐘。**暖到收斂的協定會吸收冷快取的影響**,
  而不吸收的話那個協定本來就不成立
- **[50% 這個門檻是一次觀測訂的]** → 只有「乾淨 17.95% / 退化 91.29%」這一組對照。
  但兩邊各有兩倍餘裕,而且它是**可調參數**;真正的保險是 D4 的反向驗證,不是門檻的精確度
- **[可能還有第二個累積物]** → D5 已經寫下處置。**這正是為什麼 D2 用通用的容器記憶體而非 multixact 專屬檢查**
- **[重建 postgres 讓每組的資料庫快取全冷]** → 對八組是**同等**的影響,不偏袒任何一組。
  而偏差才是本支要消除的東西,共同的成本不是

## Migration Plan

**不改動應用程式碼,無 schema 變更,無相依變更。**

改動集中在兩個檔案:

- `k6/run-comparison-matrix.sh`:每組的重建加上 `postgres-perf`
- `k6/run-load-test.sh`:新增量測前的環境健康守則

**`run-comparison-matrix.sh` 的順序與旋轉邏輯不動** —— 那是第 13 支驗證過的部分。
