## Context

Phase 1 的成功標準寫在 `openspec/project.md`:

> README 能放出四層策略 **× 兩種執行緒模型**的比較表,涵蓋正確性(是否超賣)與效能(QPS / P99 / **失敗率**),且每個數字都有可重跑的 k6 腳本支撐。

**目前只有一半。** 第 10 支重跑的四組全部是 `VIRTUAL_THREADS=false`;第 4 支確實量過虛擬執行緒,但只有第 0 層,而且是冷啟動、1.2 秒窗口的舊制 —— 第 10 支已判定那類數據不可靠。

**失敗率也一直沒收。** 有 QPS、P99、超賣、售出,但沒有把錯誤率當成一欄記錄,而它明列在成功標準裡。

還有一條既有的 spec 需求現在**不成立了**:

> `八組數據的取得流程`:啟動兩次,每次啟動內依序切換四種策略。策略可於執行期切換,同一次啟動內 MUST NOT 為了換策略而重啟。

那是第 4 支寫的,當時還不知道暖機的重要性。第 10 支的實測改變了前提 —— 見 D1。

## Goals / Non-Goals

**Goals:**

- 取得完整的八組數據(四層 × 兩種執行緒模型),全距皆 < 10%
- **失敗率**進入輸出與總表
- 更正 `八組數據的取得流程`,並說明為什麼原本的做法現在是錯的
- 對「虛擬執行緒有沒有用」給出**有依據的解讀**,而不只是報數字

**Non-Goals:**

- **不改動任何應用程式碼** —— 虛擬執行緒由 `spring.threads.virtual.enabled` 控制,已經可用
- **不調整連線池以「讓虛擬執行緒表現更好」** —— 見 D3。那會讓八組數據不可比較
- **不寫 README** —— 那是下一支。八組數據齊了才寫得出完整的表

## Decisions

### D1. 每一組都獨立重啟並各自暖機 —— 更正第 4 支的流程

原本的流程是「啟動兩次,每次啟動內依序切換四種策略」,理由是策略可於執行期切換,不必為換策略而重啟。**那個理由本身沒錯,但它與暖機不相容。**

**第 10 支實測:暖機讓吞吐從 877 變成 2607 req/s —— 三倍。** 暖機的意義是讓 JIT 進入穩態,而 JIT 的狀態是**跨策略累積**的:同一次啟動內先跑無鎖再跑悲觀鎖,悲觀鎖拿到的是一個已經被無鎖的程式碼路徑編譯過的 JVM。

四種策略共用大量程式碼(controller、facade、value object、持久化 adapter),因此污染是實質的,不是理論上的。

**更正後的流程:每一組獨立 `--force-recreate` 重啟,各自暖機一次。**

代價是八次重啟(每次約 30–40 秒),總時長增加約五分鐘。**那是為了讓八組數據可比較所付的錢。**

**不選「保留舊流程,只在切換策略後多跑一次暖機」**:暖機能讓 JIT 前進,但無法讓它**回到**未編譯的狀態。已經被前一種策略觸發的內聯與去最佳化不會消失。

### D2. 失敗率取自 k6 的 `http_req_failed`,而且它的定義要寫清楚

k6 預設把 4xx / 5xx 都算成失敗。**但本專案的 409 是預期中的正常結果** —— 庫存不足、超過限購、重試耗盡都回 409,而那些正是策略在正確運作的證據。

因此:

- **`http_req_failed` 照實記錄**,但同時記錄它的組成
- **真正該警戒的是 5xx** —— 那才是系統故障。四層的驗收都要求 5xx 為 0

**不選「把 409 排除掉再算失敗率」**:那會讓「賣完了」與「系統掛了」在同一個數字裡消失。兩者都要看得見,只是意義不同。

### D3. 連線池維持 50 不動 —— 而且這正是解讀的關鍵

虛擬執行緒的賣點是「阻塞時不佔用 OS 執行緒」。但**前三層的每一次阻塞最終都要透過 JDBC 連線**,而連線池上限是 50。

**一萬個虛擬執行緒仍然只能有 50 個同時持有連線。** 如果瓶頸在連線池,虛擬執行緒就沒有發揮空間 —— 它讓「等待」變便宜了,但等待的隊伍長度沒有改變。

**因此若八組數據顯示虛擬執行緒幾乎沒差,那不能直接推論「虛擬執行緒沒用」。** 正確的說法是「**在本專案的瓶頸位置上,執行緒模型不是限制因素**」。

這與第 6 支的 lesson 是同一件事的另一面:「加鎖之後變慢了,先確認瓶頸是不是連線池」。

**刻意不為了讓虛擬執行緒好看而調大連線池:** 那會同時改變兩個變數,八組數據就不再是「只差執行緒模型」的對照。想驗證這個推論的話,那是另一支 change 的事(連線池 × 執行緒模型的對照),不是本支。

### D4. 第 3 層是唯一預期不受益的一層,而理由要能事先說清楚

| 層 | 主要阻塞點 | 預期是否受益 |
| --- | --- | --- |
| 無鎖 | 資料庫 I/O | 可能 |
| 悲觀鎖 | 等列鎖 + 資料庫 I/O | **最有可能** |
| 樂觀鎖 | 重試的多次 round trip | 可能 |
| Redis 預扣 | 幾乎不阻塞(記憶體操作 + 非同步落庫) | **最不可能** |

**事先寫下預期,是為了讓「結果與預期不符」變成一個要解釋的事實,而不是一個可以事後合理化的數字。** 若第 3 層反而受益最多,那代表我對它的瓶頸判斷錯了,而那個錯誤本身值得記錄。

## Risks / Trade-offs

- **[八組數據的取得時間約 15–20 分鐘]** → 每組獨立重啟 + 暖機 + 三次量測。這是 D1 的代價
- **[虛擬執行緒可能全面沒差,看起來像白做]** → **那也是結論,而且是有價值的結論** ——
  它會指出本專案的瓶頸不在執行緒模型。**不得因為數字不有趣就不報**
- **[k6 的 `http_req_failed` 把 409 算成失敗,數字會很難看]** → D2 已處理:照實記錄並拆解組成。
  無鎖的失敗率會接近 0(它幾乎全部成功,那正是問題),其餘三層會有大量 409 —— **那是正確運作的證據**
- **[虛擬執行緒在高併發下可能出現 pinning]** → 若觀察到異常,照實記錄。
  本專案沒有 `synchronized` 包住阻塞操作,理論上不該發生,但理論與實測不同時要以實測為準
