## 2. 量測協定的三次修正 —— 本支真正的工作

原訂只是「跑八組」,實際上八組跑不出可用的數據,連續發現三個問題。

- [x] 2.1 **第一次修正:腳本會靜默死掉。**
      `current_strategy()` 用 `grep` 讀啟動記錄,找不到就回 1,而 `set -e` 讓
      `STRATEGY_IN_USE=$(current_strategy)` 中止腳本 —— **那行在任何 echo 之前,
      於是連一個字都不會輸出**,看起來像什麼都沒發生。已改為重試 30 秒並明確報錯
- [x] 2.2 **第二次修正:固定輪數的暖機必然低估,而且低估幅度隨層而異。**

      Redis 預扣在固定輪數下,量到的數字隨輪數**單調上升**:
      1 輪 → 3810、2 輪 → 5219、3 輪 → 8130 req/s。**每加一輪就更高一截。**
      而每次的第 1 輪都落在 1600～1800 —— 那正是「完全沒暖」的水位。

      **我一度把這個現象誤診為「主機退化」** ——
      因為重建容器後量到 1800,而一小時前是 4964。我甚至請使用者停掉其他專案的容器,
      結果沒有任何改善(仍是 1877)。**真正的原因是我把累積的暖度重建掉了**,
      早先的 4964 是在一長串測試之後量的,系統早已深度暖化。

      改為**暖到收斂**:連續兩輪差距 < 5% 才開始量測,上限 10 輪。
      實測 Redis 預扣需要 5～6 輪(5655 → 21209 → 24262 → 25597 → 24987)
- [x] 2.3 **第三次修正:重置沒有清掉 WAL。**
      悲觀鎖在暖機收斂後,三次量測仍**單調遞減**(4572 → 4246 → 3953)。
      `TRUNCATE` 清得掉資料表,清不掉 WAL,而壓測環境的 postgres 資料在 tmpfs(記憶體)——
      每輪兩萬五千次 UPDATE 加同量 INSERT,WAL 累積直接吃掉可用記憶體。
      重置加入 `CHECKPOINT` 後全距由 **14.6% 降到 6.0%**,且不再單調

## 4. 判定與收尾

- [x] 4.1 **能下的結論(差距大於較不穩定那一方的全距):**
