## Context

第 18 支在解除 postgres 飽和之後,留下一個**確定但無法解釋**的觀察:

| 指標 | P200 | P1000 | V | 判定 |
| --- | --- | --- | --- | --- |
| app CPU 毫秒/請求 | 0.249 | 0.258 | 0.248 | **三組分不出差異** |
| postgres 毫秒/請求 | 0.398 | 0.396 | **0.348** | **V 明確低 12%**(兩個比較都成立) |
| 吞吐 | 7314 | 7410 | **6907** | V 較低(對 P1000 可下結論) |

**虛擬每請求用掉的 CPU 不比平台多、postgres 端甚至明確更少,而吞吐較低,
且沒有任何容器飽和**(app 35～55%、pg 48～57%、節流 0)。

這三件事合起來只能推出一件事:**時間花在「不在 CPU 上」的地方。**
而 CPU 探針量不到那是什麼。

最明顯的候選是**連線池**:連線池上限 50,而虛擬執行緒讓約 1000 個請求同時抵達,
平台(准入 200)只讓 200 個抵達。

**但這個候選有一個明顯的問題,必須先講:** 若連線池是唯一的瓶頸,
**兩者的吞吐應該相等** —— 池限流之下吞吐 ≈ 50 ÷ 服務時間,
而 V 的 postgres CPU/請求還更低,照理應該更快而不是更慢。

**所以本支很可能會排除連線池,而不是證實它。** 那也是結果 ——
它把搜尋範圍縮小,而不是再留下一個沒有證據的說法。

## Goals / Non-Goals

**Goals:**

- 量出**每請求在連線池上花掉的時間**,並與既有的 CPU 毫秒/請求並列
- 分開「等待取得連線」與「持有連線」—— 那是兩件不同的事
- 依事先寫下的判準,**證實或排除**連線池作為那段「不在 CPU 上」的時間

**Non-Goals:**

- **不改動任何策略的實作、不改 schema、不改量測參數**
- **不開放 actuator 端點** —— 見 D2
- **不引入新的相依** —— Micrometer 與 HikariCP 已在 compile scope
- **不追「若不是連線池,那是什麼」** —— 那要等本支的結果才知道往哪找

## Decisions

### D1. 量累計的 Timer,不量瞬時的等待執行緒數

`HikariPoolMXBean.getThreadsAwaitingConnection()` 是**瞬時值**,要用它就得在量測期間取樣 ——
而取樣的問題與 `docker stats` 相同:**取樣器本身會參與被量測的系統**。

Spring Boot 在 Micrometer + HikariCP 都在 classpath 時會自動註冊兩個 Timer,兩者都是**累計**的:

| Timer | 回答的問題 |
| --- | --- |
| `hikaricp.connections.acquire` | **等**連線等了多久 |
| `hikaricp.connections.usage` | 拿到之後**持有**了多久 |

**兩個都要。**「等比較久」與「拿到之後佔比較久」是完全不同的兩件事,
只看其中一個會誤判 —— 這與第 17 支「user / system 必須拆開」是同一個道理。

前後相減再除以已知的請求數,得到**毫秒/請求**,與既有的 CPU 毫秒/請求同單位、可並列。

### D2. 從 `MeterRegistry` 讀,不開 actuator 端點

`application.yml` 刻意只暴露 `health`,理由寫在註解裡:
**「env / configprops / heapdump 會洩漏設定與記憶體內容,而本專案之後要 public」**。

**為了量測而擴大應用對外暴露的面,是拿正式環境的風險換一次實驗的方便。** 不做。

(另外 perf profile 不開主機埠,走 HTTP 還得再起一個容器來 curl,更麻煩。)

### D3. 以「定期把累計值印進應用日誌」提供取樣點

腳本已經在讀應用日誌(當前策略、准入上限都是這樣拿的),沿用同一條路。

應用每 N 毫秒輸出一行帶固定標記的累計值;腳本取 k6 執行**前後各一行**相減。

**括號的鬆緊不影響結果**:分母是已知的請求數而不是時間,
而閒置期間不會產生連線取得 —— 多包到的空白時間貢獻為零。

**但括號必須排除暖機** —— 那一段會狂打連線池。沿用 CPU 探針既有的括號位置。

**預設關閉**(間隔為 0),只有 perf profile 打開。一般執行完全不受影響。

### D3b. 這與 `RetryStatisticsLogger` 已寫下的立場衝突,必須正面處理

`RetryStatisticsLogger` 的 Javadoc 明白寫著:

> **為什麼在關閉時輸出而不是定期輸出:** 壓測期間的任何 I/O 都會影響被量測的數字。
> 關閉時只印一行,對測量結果零影響。

**那個立場是對的,而本支確實違反它。** 理由與處置:

**為什麼「關閉時輸出」在這裡不夠用:** 關閉時拿到的是**自啟動以來的累計值**,
而那包含暖機 —— 暖機最多 10 輪、正式量測 1 輪,**暖機會主宰整個數字**。
本支需要的是量測窗口內的差值,那需要窗口兩端各一個取樣點。

**為什麼不用「打一個特殊端點來觸發輸出」:** 專案既有原則是
**不為壓測在正式 API 開後門**(第 8 支即因此讓壓測腳本直接寫 Redis,而不是加載入端點)。

**處置:不主張「可忽略」,而是量它。** 塊 4 要跑一組「探針開 / 關」的對照,
**若吞吐差距大於全距就代表探針本身在干擾量測,那本支的做法就不成立。**

**這正是本專案對待「應該影響不大」的一貫方式** ——
第 17 支的 Hard Rule 說的就是:沒有量測就不要寫下機制,而「探針成本可忽略」也是一個機制宣稱。

### D4. 事先寫下三種結果的處置

| 結果 | 結論 |
| --- | --- |
| **V 的等待/請求明顯較高** | 瓶頸是連線池 —— 虛擬把更多請求擠到同一個 50 連線的閘門前 |
| **三組分不出差異** | **不是連線池** —— 本探針排除它,並指出下一個該量的東西 |
| **平台的等待反而較高** | 與假說相反,需要重新想 |

**判準一律是「差距須大於較不穩定那一方的全距」。**

**第二種結果的機率不低**(見 Context 的推理),而它一樣算成功 ——
**排除一個候選,與證實一個候選,對「縮小搜尋範圍」的價值相同。**

### D5. 持有時間要與 postgres CPU 對照著看

`usage`(持有連線的時間)包含了資料庫實際做事的時間。
而我們已經有 **postgres CPU 毫秒/請求**。

- 持有時間 ≈ postgres CPU 時間 → 連線被佔著的期間都在做事
- 持有時間 ≫ postgres CPU 時間 → **連線被佔著卻沒在做事**(等鎖、等網路、等應用端處理)

**這個對照不需要額外量測,兩個數字都已經在手上。**

## Risks / Trade-offs

- **[定期日誌在量測期間執行]** → 每秒一行,可忽略。**但它確實是量測期間的活動**,
  因此三組都開、成本相同,且間隔可設定
- **[Spring Boot 的 Hikari metrics 自動組態可能沒生效]** → 塊 1 先驗證 meter 確實存在,
  **沒有就大聲失敗**,不要輸出 0 當成「沒有等待」
- **[本支只能排除或證實連線池,不保證解出那段時間]** → D4 已寫明。
  **排除也是進展**
- **[`usage` 的語意包含應用端持有連線的整段期間]** → D5 的對照即為此,
  不把它單獨解讀

## Migration Plan

**不改 schema,無相依變更,四層策略的實作一行不動。**

- 新增一個 infrastructure 元件,定期輸出連線池的累計 Timer(預設關閉)
- `compose.yml`:perf profile 打開它
- `k6/run-load-test.sh`:於既有的 CPU 括號位置一併取前後兩點,輸出毫秒/請求
- `k6/run-comparison-matrix.sh`:欄位收進逐組輸出與 TSV
