## 4. 判定與收尾

- [x] 4.1 **回答本支的核心問題:虛擬執行緒的高變異是模型造成,還是時間順序造成?**

      | 結果 | 意義 |
      | --- | --- |
      | 虛擬組全距降到與平台組相當 | 先前的觀察是時間順序造成的,**第 11 支的觀察被推翻** |
      | 虛擬組全距仍明顯較高 | **那是執行緒模型本身的性質**,此時才有資格這樣說 |
      | 漂移 > 15% | 環境無法支撐這個比較,這也是結論 |

      **三種都算成功。目的是讓問題可回答,不是讓虛擬執行緒贏。**

      **答案是第三種:環境無法支撐這個比較(漂移 21.2%)。**
      而依 D3,這個結果的價值在於它**指出了下一步** —— 根因已追到底:

      **`pg_multixact` 在批次期間累積到 679MB,佔掉 postgres 容器 1GB 上限的 68%。**

      1. `V1__init_schema.sql:33` —— `purchase_order.event_id REFERENCES event(id)`。
         每一筆 insert 都要對**同一個** `event` 列做 FK 檢查,取 `FOR KEY SHARE` 鎖
      2. 1000 併發同時持有同一列的共享鎖 → PostgreSQL 配置 **MultiXactId** 記錄「誰和誰同時鎖著」
      3. 24 次 × 50000 個請求 = **120 萬筆 insert,全部指向同一個父列**
      4. 四個資料庫的 `datminmxid` 全部仍為 **1** —— `pg_multixact` **從未被截斷**
      5. 資料目錄在 **tmpfs(記憶體)**,679MB 直接算進容器的 1GB 上限 → 容器 **91.29%**
      6. 整批最後一筆量測(`V_noLock`,t=2342s)崩到 **1084 req/s**,同組前兩輪為 4864 / 4665

      **實測對照:**

      | 做法 | `pg_multixact` | 容器記憶體 |
      | --- | --- | --- |
      | 批次結束時 | 679M | 91.29% |
      | `VACUUM (FREEZE)` 三張表 + `CHECKPOINT` | 679M(沒動) | 91.29% |
      | 重建 postgres-perf 容器 | **16K** | **17.95%** |

      `VACUUM FREEZE` 讓 `event.relminmxid` 前進(2999734 → 3049724),但 `datminmxid` 仍為 1 ——
      截斷看的是**整個 cluster 的最小值**,而 `template0` 的 `datallowconn=false` 碰不到。
      **在單一容器的生命週期內,這個累積清不掉。**

      **為什麼第 11 支沒發現:** 那批只有 8 次量測,這批 24 次 —— 三倍的寫入量。
      而第 11 支加的 `CHECKPOINT` 修的是 **WAL**(本批 pg_wal 僅 64M,完全正常),是另一個機制。
      **`TRUNCATE` 清不掉、`CHECKPOINT` 清不掉、`VACUUM FREEZE` 也清不掉。**

      修正動到 `run-load-test.sh` 與 compose,**明文屬於本支的 Non-Goals**,
      因此另開 `fix-perf-db-multixact-accumulation`,數據於該支取得。
- [x] 4.2 在交錯之後重新判定「虛擬 vs 平台」與「無鎖 vs 悲觀鎖」——
      **差距小於較不穩定那一方的全距時,仍然不得下結論**

      但交錯本身確實生效了,這是方法上的收穫(僅為訊號,不得寫入交付物):

      | 組別 | 本批全距 | 第 11 支全距 |
