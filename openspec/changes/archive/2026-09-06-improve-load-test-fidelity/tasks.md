## 1. 腳本重構:暖機、重複量測、離散度

- [x] 1.1 `reset_data()` / `run_k6()` / `drain_async_persistence()` 抽成函式。
      **重置只有一份實作**,暖機與正式量測都走它
- [x] 1.2 **暖機**:正式量測前完整跑一次並丟棄,參數與正式那次完全相同
- [x] 1.3 **重複量測**:`RUNS=n`(預設 1),每次之間重置
- [x] 1.4 輸出含每次的值、中位數、全距;跑一次時明示「全距 0 代表沒有可信度資訊」
- [x] 1.4b **踩到一個會讓修正看起來比實際好的陷阱:全距的定義。**
      我先前口頭引用的「無鎖 72%、Redis 預扣 48%」用的是 `(max−min)/min`,
      而腳本算的是 `(max−min)/median` —— **同一組數字算出 52.5% 與 38.4%**。
      換個分母就能讓修正「看起來有效」。定義已寫死並印在輸出裡,
      基準線也用同一個定義重算 —— **比較前後必須用同一把尺**
- [x] 1.5 正確性欄位取最後一次量測,並標明「每次都應相同,不同即代表有東西壞了」
- [x] 1.6 不帶參數執行 = 暖機一次 + 量測一次,與既有用法相容
- [x] 1.7 **驗證**:`bash -n` 通過;`./mvnw verify` 綠(147 個測試,應用未受影響)

## 2. 量測與判定

- [x] 2.1 pessimistic × 3 —— **暖機本身有效,但結果是壞的**:
      暖機自己跑出 877 req/s(與舊的 813 幾乎相同),而暖機後的正式量測是
      **2607 req/s** —— 快了三倍。**舊的四層數據全部都在量冷啟動的 JVM,
      量到的大約只有實際穩態的三分之一。**

      但三次的全距是 **75.7%** —— 悲觀鎖原本是最穩定的一層(0.8%)
- [x] 2.2 **判定:未達標。而且成因與直覺相反。**

      | | 吞吐 | 1000 個請求的窗口 |
      | --- | --- | --- |
      | 暖機前 | ~813 req/s | ~1.23s |
      | 暖機後 | ~2600 req/s | **~0.38s** |

      **暖機讓系統變快,反而把量測窗口壓得更短** —— 一次 200ms 的 GC 停頓
      就能砍掉一半吞吐。暖機沒有解決問題,它**揭開**了真正的問題:窗口太短。

      **這正是「先量再決定」的價值。** 若當初一次改到位,我會以為是兩個修正
      共同奏效,而永遠不知道暖機單獨會讓情況變糟
- [x] 2.3 未達標 → 進塊 3(原訂的 2.3 / 2.4 逐層量測併入塊 3 之後一次完成)

## 3. 放大爆發規模

- [x] 3.1 庫存 500 → **25000**、請求 1000 → **50000**,維持 2:1 ——
      競爭仍集中在同一列庫存上,策略之間的比較性質不變,只是窗口從 0.4 秒變成約 2 秒
- [x] 3.2 **使用者識別碼改為每請求唯一**(`__VU × 100000 + __ITER`),冪等鍵同理。
      不改的話同一個 VU 送第 5 次就撞上限購上限 4,量到的會變成限購拒絕的吞吐
- [x] 3.3 未改成「固定 VU 持續 N 秒」—— `purchase-rush.js` 既有的理由仍然成立
- [x] 3.4 **判定:四層全部達標。**

      | 策略 | 修正前全距 | 修正後全距 | 達標 |
      | --- | --- | --- | --- |
      | noLock | 52.5% | **0.5%** | ✅ |
      | pessimistic | 0.8%(→ 暖機後一度惡化到 75.7%) | **0.2%** | ✅ |
      | optimistic | 2.3% | **2.9%** | ✅ |
      | redisPreDeduct | 38.4% | **4.8%** | ✅ |

- [x] 3.5 **另外修掉一個從第 8 支就潛伏的 bug:壓測的 Redis 重置從來沒有生效。**

      原本寫成 `redis_cli --scan --pattern 'purchased:*' | xargs -r redis_cli DEL`,
      而 **`redis_cli` 是 shell function —— `xargs` 無法執行 shell function**,
      它 exec 的是真正的執行檔。錯誤被 `2>&1 || true` 吞掉,完全沒有徵兆。

      **第 8 支沒有暴露它**:當時每個使用者每輪只買 1 張、只跑三輪,
      累計 3 張仍在限購上限 4 以下,售出數每次都正好 500。放大成每 VU 50 次之後,
      使用者在第四輪撞上限購 —— 症狀是「50000 個請求只賣出 3104 張,
      而吞吐數字看起來很漂亮」。**那個漂亮的數字量的是限購拒絕的吞吐。**

      修法:掃描與刪除都在容器內以單一 `sh -c` 完成
- [x] 3.6 `design.md` 的 Open Questions 結案:**需要放大窗口**,依據見 2.2

## 4. 四層數據與收尾

- [x] 4.1 **四層各跑 3 次(暖機另計),全部條件相同:**

      | 層 | 策略 | 各次 req/s | 中位數 | 全距 | avg | p(99) | 售出 | 超賣 |
      | --- | --- | --- | --- | --- | --- | --- | --- | --- |
      | 0 | noLock | 4979 / 4978 / 5002 | **4979** | 0.5% | 177–188ms | 297–300ms | 50000 | **48891** |
      | 1 | pessimistic | 4629 / 4636 / 4627 | **4629** | 0.2% | 206–212ms | 396–419ms | 25000 | 0 |
      | 2 | optimistic | 2962 / 3046 / 2960 | **2962** | 2.9% | 325–336ms | 991ms–1.01s | 25000 | 0 |

      第 2 層:最大嘗試 100(觸頂)、平均 4.86、重試耗盡 1。

      對帳間隔 1000ms、重試上限 100、postgres 2 核 / 1GB / `max_connections=500` / tmpfs、

      1000 VU × 50 次 = 50000 個請求、初始配額 25000、限購上限 4、macOS + OrbStack。

- [x] 4.2 **結論(全部與修正前不同):**

      **① 正確性的代價是 7.0%,不是 16%。** 無鎖 4979 vs 悲觀鎖 4629 ——
      而兩者的全距是 0.5% 與 0.2%,這個差距是實的。
      第 6 支量到的 -16% 是冷啟動下的數字,已知不可靠。

      **② 樂觀鎖比悲觀鎖低 36%。** 方向與第 7 支一致(當時 -42%),
      但現在兩邊的全距都在 3% 以內,這個結論站得住。

      **③ Redis 預扣的受理速率是悲觀鎖的 5.0 倍,完成速率是 2.2 倍。**
      這是修正前完全下不了的結論(當時三層區間互相重疊)。
      **兩個數字都要報**:23274 req/s 是**受理**速率,回應時訂單還不存在;
      把落庫收斂的 2.8 秒算進去,完成速率是 10104 req/s。

      **④ 延遲的差距比吞吐更懸殊:** 第 3 層 avg 40–42ms、p99 80–134ms,
      悲觀鎖是 206–212ms / 396–419ms —— **五倍與三倍**。
      非同步落庫真正買到的是使用者的等待時間
