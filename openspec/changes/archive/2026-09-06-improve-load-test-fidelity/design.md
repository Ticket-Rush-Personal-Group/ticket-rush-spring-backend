## Context

Phase 1 的成功標準是「README 能放出四層策略的比較表」。**那張表目前下不了結論。**

第 8 支以同一個 build、同一個 session、完全相同的條件連續量測:

| 策略 | 各次 req/s | 全距 |
| --- | --- | --- |
| noLock | 494 / 682 / 852 | **72%** |
| pessimistic | 810 / 816 | 0.8% |
| optimistic | 463 / 474 | 2.3% |
| redisPreDeduct | 522 / 649 / 771 | **48%** |

能明確下的結論只有「樂觀鎖最差」,其餘三層的區間互相重疊。**這不是數字不好看,是核心產出失效。**

已經查清楚的兩個成因(第 8 支的 7.5 與 tasks 記錄):

1. **完全沒有暖機,而且每組都是剛啟動的 JVM。** 那 1000 個請求打的是還沒經過 JIT 的程式碼 —— 整場壓測都在暖機階段裡
2. **量測窗口只有 1.5 秒左右**(1000 VU × 1 iteration),任何背景雜訊都會佔掉可觀的比例

穩定與否本身有成因,這一點第 8 支已經觀察到:**被硬性序列化點卡住的策略**(悲觀鎖的列鎖、樂觀鎖的 CAS 競爭)吞吐極穩定,因為瓶頸在系統內部,機器的閒忙影響不到它;**沒有這種瓶頸的策略**則直接反映機器當下的狀態。

## Goals / Non-Goals

**Goals:**

- 同一設定連續三次的吞吐全距 **< 10%**(現況 72% / 48%)
- 壓測的輸出**強迫誠實**:單一數字不再是合法的輸出形式
- 四層數據重跑,`tasks/todo.md` 的總表更新為可下結論的版本

**Non-Goals:**

- **不推翻既有的 burst 設計** —— 見 D3。`purchase-rush.js` 既有的理由仍然成立
- **不改動任何應用程式碼** —— 本支只碰壓測工具。四層策略的行為一個字都不動
- **不回頭改寫已 archive 的 change 文件** —— 它們是歷史紀錄,記載「當時量到什麼、當時怎麼想」。
  回頭改寫會抹掉這個專案最有價值的東西(學習軌跡)。只更新 `todo.md` 的總表與 `lessons.md`
- **不先做「放大量測窗口」** —— 見 D2。先驗證暖機是否已足夠,那是實驗而不是推斷

## Decisions

### D1. 暖機必須是一次**完整的**壓測,而且參數與正式那次完全相同

**不是「先打幾個請求熱一下」。** JIT 的編譯門檻以呼叫次數計(C2 約一萬次),打十個請求暖不到任何東西。暖機必須跑完整的負載,走完整條路徑 —— 包含 Lua 腳本、Stream 投遞、非同步落庫。

**參數必須與正式那次相同(VU 數、庫存、策略)。** 用較小的負載暖機會讓 JIT 走上不同的分支路徑,而且連線池、PostgreSQL 的 buffer cache 都不會進入正式量測時的狀態。

**暖機的結果必須丟棄,而且資料要重置。** 重置 MUST 走與正式那次完全相同的程式碼路徑 —— 另寫一套重置邏輯必然漂移,而漂移的症狀是「第一次跑的初始狀態與後續不同」,那正好是我們要消除的東西。

### D2. 先只做暖機,量了再決定要不要放大窗口

**這是實驗而不是推斷。** 冷啟動的 JVM 是我判斷的主因,但那是判斷,不是量測結果。

流程:加上暖機 → 同設定量三次 → 看全距。**若已 < 10%,就不做放大窗口** —— 那項要改動使用者識別碼的產生方式(每請求唯一,否則會撞限購)、庫存與請求數的比例,以及每次壓測的時間。不必要的話不做。

**不選「一次改到位」**:兩個變更一起下,若結果仍不穩,無法分辨是哪一個沒生效;若結果穩了,也不知道是不是其中一個就夠了。**一次只動一個變數,是這個專案從第 6 支的連線池對照就開始用的手法。**

### D3. 放大窗口的話,是「把爆發放大」而不是「把爆發拉成穩態」

若 D2 的量測顯示需要放大,做法是庫存與請求數**同步**放大(維持目前 2:1 的比例),而不是改成固定 VU 持續 N 秒。

`purchase-rush.js` 既有的註解已經寫明理由:「搶票的本質是瞬間爆發,不是穩態負載」、固定 VU 持續 N 秒「會在庫存賣完後變成量測 409 回應的吞吐」。**那個理由現在仍然成立,本支不推翻它。**

放大時有一個必須處理的細節:目前使用者識別碼是 `__VU`,一個 VU 送多次請求會撞到限購上限 4 —— 量到的會變成限購拒絕。識別碼要改成每請求唯一(`__VU` 與 `__ITER` 的組合)。

### D4. **輸出格式必須強迫誠實:沒有全距的吞吐數字不是合法的輸出**

這是本支最重要的一項,而且它不是「順便加個統計」。

**目前腳本輸出單一數字,那個格式本身就在鼓勵「量一次就寫進表格」** —— 第 8 支之前的每一支都是這樣做的,包括我自己在第 6、7 支寫下的數據。直到第 8 支連續量了三次才發現問題。

因此腳本 SHALL 支援跑 N 次,並**一律輸出:每次的值、中位數、全距**。跑一次時全距為 0,而那個 0 本身就是提醒 ——「你只量了一次」。

**用中位數而非平均。** 平均會被離群值拉走(無鎖的 494 vs 852,平均會落在一個從未出現過的值上);中位數對三次量測是穩健的。

**「量幾次」由執行的人決定,不寫死在腳本裡。** 第 8 支已經發現次數需求隨策略而異(有內部序列化瓶頸的量一次就夠),但把那個結論寫進腳本等於把它固化 —— 而它是一個觀察,不是一條規則。

### D5. 驗收條件可證偽,而且達不到時不准降低標準

**同一設定連續三次的吞吐全距 < 10%。**

現況是 72% 與 48%。**若修完仍達不到,照實記錄實際的全距,並更正判準且說明為什麼** —— 例如改為「20% 以內,且比較的差距必須大於全距才可下結論」。

**SHALL NOT 以「感覺穩定多了」結案**,也不得挑選較好的那幾次。這條寫在這裡,是因為它正是最容易在收尾時被悄悄放寬的東西。

## Risks / Trade-offs

- **[壓測總時長增加]** → 每組多一次完整的暖機,加上量三次,四層約需 8–10 分鐘(原本約 6 分)。
  **這是為了讓表格能下結論所付的代價,不是浪費**
- **[暖機本身可能不夠]** → D2 的流程就是為此設計的:量了才知道。不夠就進到放大窗口
- **[機器上的其他活動仍會影響]** → 本支處理的是系統本身造成的變異(冷啟動、窗口過短)。
  外部干擾無法在腳本層消除 —— **能做的是把它量出來(全距)並誠實呈現**,而不是假裝它不存在
- **[中位數在只跑兩次時無意義]** → 兩次的中位數等於平均。輸出會照實顯示次數,由讀的人判斷

## Migration Plan

**不改動任何應用程式碼,無 schema 變更,無相依變更。**

`k6/run-load-test.sh` 重構為可重複執行;`k6/purchase-rush.js` 僅在 D3 生效時才需要改。
既有的呼叫方式(不帶參數直接執行)行為不變 —— 預設為「暖機一次 + 量測一次」。
