## ADDED Requirements

### Requirement: Redis 預扣策略

第 3 層策略 SHALL 以 Redis 作為**准入控制**、以資料庫作為**最終帳本**,兩者不對等。

Redis 決定「誰可以買」,資料庫記錄「誰買到了」。**超賣的定義因此完全不變**:資料庫的訂單張數總和是否超過初始庫存。Redis 已扣但尚未落庫的部分 SHALL NOT 被計為超賣 —— 它是**待收斂的差額**。

**MUST NOT 將 Redis 視為最終帳本。** 那會讓「超賣」的定義隨策略而變,四層就無法用同一把尺量。在一個以比較為唯一產出的專案裡,判準不得跟著被比較的對象一起改變。

**預扣的原子性:**

扣減 SHALL 以**單一 Lua 腳本**完成,且**限購檢查與庫存檢查 MUST 位於同一支腳本內**。

限購若留在應用端判斷(讀 Redis → 判斷 → 扣),即為 check-then-act:兩個併發請求會讀到相同的已購數並各自通過檢查。**那正是第 0 層的缺陷,只是換一個儲存體重演一次。**

腳本 SHALL 以不同的回傳碼區分「超過限購」、「庫存不足」、「場次未開賣」三種失敗 —— 呼叫端對三者的處置不同(放棄 / 換場次 / 稍後再來)。

**庫存 key 不存在 MUST 視為「場次未開賣」而非「庫存無限」。** 把「不知道」當成「可以」是超賣最廉價的來源。

**非同步落庫:**

預扣成功後 SHALL 將訂單寫入 Redis Stream,由 consumer group 消費並落庫。

**MUST NOT 使用取出即離開佇列的載體**(如 `BLPOP`)或**行程內佇列**:前者在落庫前崩潰時無聲掉單且不留痕跡,後者重啟即全失且其佇列長度會成為隱形背壓,使該層的吞吐被高估。

順序 SHALL 為「落庫成功才 ack」:

| 情況 | 處置 |
| --- | --- |
| 落庫成功 | `XACK` |
| 落庫失敗 | 回補 Redis 庫存與已購數 → `XACK` |
| 消費者崩潰 | 不 ack,訊息留在 pending 供重新領取 |

**重複落庫 MUST 由冪等鍵擋下。** 「回補成功、`XACK` 之前崩潰」這個窗口無法消除:訊息會被重新領取並再次落庫,而庫存已回補 —— 那是真的超賣。因此落庫撞上冪等鍵唯一約束時 SHALL 視為先前已成功,直接 ack 且**不得回補**。

**補償與對帳:**

即時補償與週期對帳 SHALL **兩者都有**,不得二選一。即時補償只處理「已知失敗」;崩潰、逾時、消費者被終止所造成的遺失只有對帳抓得到。

對帳的差額定義為:`(初始庫存 − Redis 餘量) − 資料庫訂單張數`。

**對帳 MUST 僅在 pending 為空時回補。** pending 中的訊息代表「仍在處理」,其造成的差額是暫時且正常的。未檢查 pending 即回補,會把處理中訂單所佔的庫存還回去,而那些訂單稍後落庫成功 —— **結果是真的超賣。**

> **對帳真正的危險不是漏補,是誤補。** 漏補的代價是少賣幾張票,誤補的代價是超賣。兩者不對等,因此對帳一律偏保守。

**MUST NOT 以「將 Redis 覆寫為 `初始庫存 − 資料庫訂單數`」的方式對帳** —— 那是誤補的最極端形式,且覆寫會與併發中的預扣互相踩踏。

**正確性驗收:**

本層的併發測試 MUST 進入預設的 `verify`,不得以 tag 隔離。

- 1000 執行緒對可用庫存 500 的場次各購買 1 張 → 資料庫訂單張數總和 SHALL **恰好等於 500**
- 同一人併發送出超過上限的請求 → 該使用者成交張數 SHALL **恰好等於限購上限**
- 注入落庫失敗後 → 差額 SHALL 最終收斂為 **0**
- pending 非空時執行對帳 → SHALL NOT 回補任何庫存

**斷言 MUST 使用「恰好等於」而非「不超過」。**

**效能量測項目:**

基本組為 QPS、P50 / P95 / P99、錯誤率。本層特有指標:

| 指標 | 說明 |
| --- | --- |
| **回應後到訂單可見的延遲** | 本層真正賣掉的東西。前三層此值為 0 |
| **對帳差額隨時間的變化** | 收斂要看得到過程,不是只看終點 |
| 重複落庫次數 | 冪等鍵擋下的次數。**大於 0 代表崩潰窗口真的發生過**,是好事不是壞事 |

**Redis 服務與對帳間隔 MUST 納入測量條件。**

**與前一層的對照:**

本層 MUST 以第 1 層(悲觀鎖)的數據為分母說明改善與代價,且測量條件 MUST 相同。

**若本層的吞吐優於前三層,MUST 同時說明它拿什麼換的** —— 回應時訂單尚不存在、需要對帳機制、多一個必須運維的元件。**只報吞吐不報代價,是本專案最該避免的那種數據。**

#### Scenario: 併發購票不超賣

- **WHEN** 1000 執行緒同時對可用庫存 500 的場次各購買 1 張
- **THEN** 資料庫的訂單張數總和 SHALL 恰好為 500
- **AND** Redis 的庫存餘量 SHALL 恰好為 0

#### Scenario: 併發下限購不被突破

- **WHEN** 單一使用者對庫存充足的場次併發送出超過上限的請求
- **THEN** 該使用者成交張數 SHALL 恰好等於限購上限

#### Scenario: 限購檢查若移出 Lua 腳本則被突破

- **WHEN** 將限購檢查自 Lua 腳本移至應用端(讀取後判斷再扣減)
- **THEN** 併發限購測試 SHALL 失敗 —— 那是 check-then-act,與第 0 層的缺陷同源

#### Scenario: 庫存 key 不存在

- **WHEN** 對一個尚未載入 Redis 庫存的場次購票
- **THEN** 回應 SHALL 為 `EVENT_NOT_ON_SALE`
- **AND** SHALL NOT 建立訂單,亦 SHALL NOT 將其視為庫存無限

#### Scenario: 落庫失敗後補償

- **WHEN** 消費者落庫失敗
- **THEN** Redis 的庫存與該使用者的已購數 SHALL 被回補
- **AND** 該訊息 SHALL 被 ack —— 已補償的訊息不得重複處理

#### Scenario: 重複落庫不造成超賣

- **WHEN** 同一則訊息因崩潰而被重新領取並再次落庫
- **THEN** 冪等鍵唯一約束 SHALL 擋下第二筆訂單
- **AND** 該情況 SHALL 被視為已成功並 ack,**SHALL NOT 觸發回補**

#### Scenario: 對帳在 pending 非空時不回補

- **WHEN** Stream 的 pending 清單非空且存在差額
- **THEN** 對帳 SHALL NOT 回補任何庫存
- **AND** 該差額 SHALL 被視為處理中而非遺失

#### Scenario: 對帳收斂

- **WHEN** 注入落庫失敗後,等待 pending 清空並執行對帳
- **THEN** `(初始庫存 − Redis 餘量) − 資料庫訂單張數` SHALL 收斂為 0

#### Scenario: 效能優勢必須連同代價一起呈現

- **WHEN** 本層的吞吐優於前三層
- **THEN** 記錄 MUST 同時列出最終一致的窗口、對帳機制的存在、以及新增的運維元件
- **AND** SHALL NOT 只呈現吞吐數字
