## Context

前五支的產出:完整的購票路徑、兩組併發缺陷的證據、可重現的壓測環境。本支加入第一個正確的實作。

四層策略置於 in port、各策略持有自己的交易邊界、port 跟著策略進來等既有決策見 `openspec/project/backend-architecture.md`。

## Goals / Non-Goals

**Goals:**

- 悲觀鎖策略,零超賣且零超買
- 解決「限購檢查落在鎖保護範圍之外」的衝突
- 連線池設定,並能區分「等鎖」與「等連線」
- 與第 0 層在相同條件下的效能對照

**Non-Goals:**

- **不修改第 0 層** —— 四層必須並存才能比較
- **不追求本層的效能最佳化** —— 它的定位就是「正確但慢」,把它調快會模糊四層的區別
- **不做鎖逾時與死鎖處理** —— 本專案只鎖單一列且順序固定,不會死鎖。加上逾時處理會引入未被驗證的錯誤路徑

## Decisions

### D1. 限購改為「鎖前快篩、鎖後權威檢查」的雙重檢查

這是本支最重要的決定,它推翻了第 5 支 D2 的單一檢查。

**衝突的本質:** 悲觀鎖鎖的是 `stock` 那一列。限購檢查讀的是 `purchase_order` 的聚合 —— 若它在取得鎖**之前**執行,就不在鎖的保護範圍內,兩個併發請求仍會讀到相同的已購數。第 5 支的證據(超買 6 張)在本層會原封不動地重現。

**但把限購移到鎖之後,又會失去第 5 支 D2 的優化**:所有請求都得先排隊取得鎖,包含那些注定被限購擋下的。在黃牛用腳本猛打的情境下,那些請求本來可以在更外層就被擋掉。

**取捨:兩次都做。**

```
1. 鎖前:快篩。讀已購數並檢查 —— 明顯超限的請求在此快速失敗,不進入鎖競爭
2. 取得 stock 的排他鎖
3. 鎖後:權威檢查。重新讀已購數並再檢查一次 —— 這次在鎖的保護範圍內
```

**不選「只做鎖後檢查」**:正確但放棄了快速失敗。限購的目的之一就是擋掉大量無效請求,讓它們全部去排隊等鎖,等於自廢武功。

**不選「只做鎖前檢查」**:那就是第 5 支的現況,限購會被突破。**正確性不能為了效能讓步。**

**代價**:多一次查詢。但它落在索引上,且只發生在通過快篩的請求上。

**一個必須說清楚的前提:鎖後檢查之所以有效,是因為它與扣庫存在同一個交易、同一把鎖之下。** 前一個交易提交後才輪到下一個,因此下一個讀得到前一個建立的訂單 —— 這正是第 3 支發現的「`synchronized` 無效」的反面:那時鎖比交易窄,現在交易在鎖之內。

### D2. 以 Spring Data 的 `@Lock(PESSIMISTIC_WRITE)` 實作,不寫原生 SQL

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from StockJpaEntity s where s.eventId = :eventId")
Optional<StockJpaEntity> findByIdForUpdate(@Param("eventId") Long eventId);
```

**不選原生 `SELECT ... FOR UPDATE`**:JPQL 加註解的版本由 Hibernate 產生對應方言的 SQL,而且 entity 會進入持久化 context —— 後續的更新走同一個 session,不需要額外的寫入路徑。原生 SQL 則要自行處理 entity 狀態,容易產生「鎖了一個物件、更新另一個物件」的錯誤。

**新增 port 而非修改既有的 `LoadStockPort`**:第 2 支的 D6 已定調 —— 各策略對外部世界的需求不同,強行收斂成單一 port 只會得到一個為了容納全部而失去意義的介面。第 0 層繼續用不加鎖的版本。

### D3. HikariCP 連線池大小明確設定為 50

目前完全沒有設定,用的是預設的 **10**。

**這個數字在本支是決定性的。** 悲觀鎖讓交易變長,而交易期間連線被佔用 —— 1000 併發下,10 個連線意味著最多 10 個請求真的在等鎖,其餘 990 個在等連線。**量到的延遲會是「排隊等連線」的延遲,而不是「鎖競爭」的延遲。**

設 50 的理由:postgres 的 `max_connections` 是 500(第 4 支已設),50 個連線遠低於上限、不會撞到資料庫端;同時足夠讓鎖競爭成為主要瓶頸而非連線數。

**這個值必須進入測量條件** —— 它會影響所有策略的數據。

### D4. 以「改變連線池大小」的實驗來區分等鎖與等連線

兩者在延遲圖表上長得一模一樣,而 metrics 的解讀容易陷入爭辯。用實驗更直接:

```
跑兩組:連線池 10 與連線池 50，其餘條件完全相同
- 若吞吐顯著改善 → 原本的瓶頸在連線池
- 若吞吐幾乎不變 → 瓶頸在鎖，連線池不是限制因素
```

**這個對照本身就是本層有價值的產出。** 它回答了一個實務上極常見的誤判:「加鎖之後變慢了」——變慢的可能不是鎖,而是連線被鎖住的時間拉長後,連線池成了新瓶頸。

### D5. 正確性測試這次是真的要綠

第 0 層的併發測試是**證據測試**(刻意紅、以 tag 隔離)。本層的併發測試是**驗收測試** —— 它必須進入預設的 `verify`,任何回歸都要立刻擋下 CI。

斷言:
- 售出張數**恰好等於**初始庫存(不是「小於等於」)
- 最終庫存**恰好為 0**
- 同一人的成交張數**恰好等於**限購上限

**用「恰好」而非「不超過」**:後者在系統完全故障、一張都沒賣出時也會通過。

## Risks / Trade-offs

- **[雙重檢查增加一次查詢]** → 落在索引上,且只發生在通過快篩的請求;實際成本由本支的數據回答。
- **[連線池 50 可能仍不是最佳值]** → D4 的對照實驗會顯示它是否為瓶頸;本支不追求最佳化,只求它不掩蓋鎖的效果。
- **[悲觀鎖在單列上不會死鎖,但這個前提未來可能失效]** → 若日後出現需要同時鎖多列的情境(例如跨場次套票),必須重新檢視鎖順序。記入 `todo.md`。
- **[本層的數據會比第 0 層難看很多]** → 那是預期且正確的結果。**不得為了讓數字好看而調整測量條件** —— 四層必須在相同條件下比較。
