## 1. 連線池設定

- [x] 1.1 `application.yml` 設定 `spring.datasource.hikari.maximum-pool-size: 50`。
      **目前完全沒有設定,用的是預設 10** —— 1000 併發下最多只有 10 個請求真的在等鎖,
      其餘 990 個在等連線,量到的會是排隊延遲而非鎖競爭
- [x] 1.2 設定值與資料庫的 `max_connections=500`(第 4 支已設)的關係要寫進註解 ——
      50 遠低於上限,不會撞到資料庫端
- [x] 1.3 `RuntimeInfoLogger` 加入連線池上限,**從 `HikariDataSource` 實例讀取而非讀設定值** ——
      與 CPU / heap 同樣的理由:報告的必須是實際生效的值。
      啟動記錄實測:`連線池上限 : 50`。
      **另加防護**:Testcontainers 的 postgres `max_connections` 提高至 300 ——
      Spring 的 context 快取保留多個 context,每個各有一個 50 上限的連線池,
      三個以上就會超過預設的 100,而症狀看起來像「偶發的測試不穩定」
- [x] 1.4 **驗證**:`./mvnw verify` 綠,啟動記錄顯示連線池大小

## 2. out port 與悲觀鎖查詢

- [x] 2.1 `LoadStockForUpdatePort`:以排他鎖取得庫存。**新增 port 而非修改 `LoadStockPort`** ——
      第 2 支 D6 已定調:各策略對外部世界的需求不同,第 0 層繼續用不加鎖的版本
- [x] 2.2 `StockJpaRepository` 加 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 的查詢方法(D2)。
      **不寫原生 SQL** —— JPQL 版本由 Hibernate 產生對應方言,且 entity 進入持久化 context,
      後續更新走同一 session,避免「鎖了一個物件、更新另一個」
- [x] 2.3 adapter 實作該 port
- [x] 2.4 `PessimisticLockBehaviourTest`:兩個真實交易競爭同一列。
      **驗兩個條件,缺一不可**:第一個持鎖時第二個必須 timeout;第一個提交後第二個必須立即完成。
      只驗前者的話,一個「永遠卡住」的實作也會通過。
      用明確的 `ExecutorService` 而非 `ForkJoinPool.commonPool()` ——
      共用池的執行緒數受核心數影響,兩個阻塞任務可能搶不到執行緒而假性失敗
- [x] 2.5 **反向驗證通過**:移除 `@Lock(PESSIMISTIC_WRITE)` 後測試變紅,還原後回綠。
      **只驗證「查得到正確資料」的測試在移除 `@Lock` 後依然全綠** —— 那種測試對鎖毫無意義
- [x] 2.6 **驗證**:`./mvnw verify` 綠

## 3. PessimisticPurchaseService

- [x] 3.1 `PessimisticPurchaseService`,bean name `pessimistic`,標註 `@Transactional`
- [x] 3.2 **限購雙重檢查**(D1):鎖前快篩、鎖後權威檢查。
      兩處都呼叫同一個 `PurchaseLimitPolicy`,差別只在時機
- [x] 3.3 流程:場次存在 → 限購快篩 → **取得庫存排他鎖** → 限購權威檢查 → 扣減 → 建單
- [x] 3.4 單元測試:流程正確、鎖前後都檢查限購、超限時不進入後續步驟
- [x] 3.5 **併發正確性測試(進入預設 `verify`,不加 tag)。實測全部通過**:
      1000 併發搶 500 張 → 售出**恰好 500**、庫存**恰好 0**、成功 500 / 拒絕 500;
      同一人 20 個併發 → 成交**恰好 4** 張。原 task 內容:
      - 1000 執行緒搶 500 張 → 售出**恰好 500**、庫存**恰好 0**
      - 同一人 20 個併發請求(上限 4)→ 成交**恰好 4** 張
      **斷言用「恰好等於」而非「不超過」** —— 後者在系統完全停擺時也會通過
- [x] 3.6 **反向驗證,兩項皆通過**:
      - 移除 `@Lock(PESSIMISTIC_WRITE)` → 售出 **1000 張**(預期 500),超賣回來了
      - 移除鎖後的權威檢查、只留快篩 → 成交 **7 張**(預期 4),**限購被突破**

      **第二項是 D1 的核心論據,而它成立了**:只有鎖前快篩的話限購擋不住併發。
      雙重檢查不是過度設計 —— 少了鎖後那次,本層就會重現第 5 支的缺陷
- [x] 3.7 **驗證**:`./mvnw verify` 綠(含新的併發正確性測試)

## 4. 壓測與對照

- [x] 4.1 以 compose 的 `STRATEGY` 環境變數切換策略。
      **另加 `POOL_SIZE` 變數**,讓連線池可在不改程式碼的情況下對照
- [x] 4.2 **三組數據**(每組的設定皆取自應用啟動記錄,非設定檔):

      | | 策略 | 連線池 | req/s | avg | p(95) | p(99) | 售出 | 超賣 |
      | --- | --- | --- | --- | --- | --- | --- | --- | --- |
      | **A** | pessimistic | 50 | 693.76 | 478.43ms | 996.33ms | 1.11s | 500 | **0** |
      | **B** | pessimistic | 10 | 510.07 | 382.28ms | 627.69ms | 897.92ms | 500 | **0** |
      | **C** | noLock | 50 | 827.58 | 699.63ms | 1.13s | 1.15s | 1000 | 978 |

      **共同測量條件**:`availableProcessors: 4`、heap 1536MB、平台執行緒、
      postgres `max_connections=500` / 2 核 / 1GB / tmpfs / fsync 開啟、
      k6 2 核 / 512MB、1000 VU 每 VU 一次請求、初始庫存 500、限購上限 4、
      READ COMMITTED、macOS + OrbStack。
- [x] 4.3 **連線池對照(A vs B)—— 判定:瓶頸在連線池,不是鎖。**

      連線池 10 → 50,吞吐從 510.07 提升到 693.76 req/s(**+36%**),其餘條件完全相同。
      若瓶頸是鎖,加連線池不會有這個幅度的改善。

      **一個容易誤讀的地方:B 的 p99 反而比 A 低**(897.92ms vs 1.11s)。
      那不代表 B 比較好 —— 連線池小的時候,同時進入系統的請求少,個別請求的延遲自然短,
      但整體吞吐更差。**這種情況下延遲指標會給出與吞吐相反的結論,判準要看吞吐。**
- [x] 4.4 **與第 0 層對照(A vs C,連線池皆 50)**:

      | | 無鎖(C) | 悲觀鎖(A) | 變化 |
      | --- | --- | --- | --- |
      | 超賣 | **978 張** | **0** | 問題消除 |
      | 售出 | 1000(錯) | 500(正確) | — |
      | req/s | 827.58 | 693.76 | **-16%** |
      | avg | 699.63ms | 478.43ms | **-32%**(反而更快) |
      | p(99) | 1.15s | 1.11s | 略降 |

      **正確性的代價比預期小得多:吞吐只降 16%,而平均延遲反而降低 32%。**

      平均延遲下降的原因值得說明:無鎖版本 1000 個請求全部走完整流程(查限購、讀庫存、
      寫庫存、建訂單),悲觀鎖版本有 500 個在庫存售罄後被快速拒絕 ——
      **被拒絕的請求便宜得多**,拉低了平均值。這也說明為什麼不能只看 avg。

      **第 4 支的第 0 層數據(884.55 req/s)不能用於此處對照** —— 那時連線池是預設 10,
      條件不同。C 組是為了匹配條件而重跑的
- [x] 4.5 三組的測量條件除了刻意變動的那一項外完全相同,無為了好看而調整
