# OpenSpec 慣例

> 自訂 schema、能力命名前綴、`strategy-*` 的驗收格式、change 命名、tasks.md 塊式切分、寫作品質基準。

> 本檔為 `openspec/project.md` 的一部分,導覽見該檔。

---

## 自訂 schema:格式規範的載體

spec / tasks 的格式規範不寫在文件裡等人自律,而是放在 fork 出來的 schema:

```
openspec/schemas/spec-driven-custom/
├── schema.yaml              # 各 artifact 的 instruction
└── templates/               # 產出檔案的骨架
    ├── proposal.md  ├── spec.md  ├── design.md  └── tasks.md
```

**建立 change 一律要帶旗標:**

```bash
openspec new change "<name>" --schema spec-driven-custom
```

`openspec config` 只支援 global scope,專案預設 schema 進不了版控 —— 少帶旗標會靜默落回內建 schema,本檔所有規範一條都不會生效。

## 能力(capability)命名

能力名稱為 kebab-case,**必須**帶四類前綴之一。前綴決定該 spec 的寫法:

| 前綴 | 內容 | 要寫 Request/Response | 要寫驗收數據 | 範例 |
| --- | --- | --- | --- | --- |
| `api-` | REST endpoint 契約 | ✅ 必寫 | ❌ | `api-ticket-purchase` |
| `strategy-` | 併發控制策略的實作與驗收 | ❌ | ✅ 必寫 | `strategy-pessimistic-lock` |
| `platform-` | 跨切面契約與工程規則 | ❌ | ❌ | `platform-hexagonal-layering` |
| `ui-` | Thymeleaf 管理介面(Phase 2) | ❌ | ❌ | `ui-admin-dashboard` |

**`strategy-` 是本專案特有的前綴。** 四層併發策略共用同一個 endpoint,它們不是新的介面契約,而是同一契約的不同實作 —— 其驗收條件是正確性與效能數據,而非請求回應格式。歸進 `api-` 或 `platform-` 會掩蓋它們是專案核心產出這件事。

- **不要為單一 endpoint 開新能力**,併進它所屬的既有 spec。
- 前台(Vue)於 Phase 3 才存在,且位於獨立 repo,屆時該 repo 自建一份 openspec。跨 repo 的 change 不存在 —— 兩個 repo 獨立版控、獨立部署。

## `strategy-*` 的驗收格式

每個 `strategy-*` 的 spec **必須**依序包含以下三段,且驗收條件必須可證偽:

### 1. 正確性驗收

以可執行的斷言表述,不得用形容詞。

- ✅ 「1000 執行緒同時購買、庫存 500,最終庫存為 0 且成功訂單張數總和為 500」
- ❌ 「不會超賣」

第 0 層(無鎖對照組)是唯一的例外:它的正確性驗收是**刻意失敗**,該測試須以獨立標記隔離並保留於 repo 中,作為問題確實存在的證據。

### 2. 效能量測項目

需明列本層要量測的指標。基本組為 QPS、P50 / P95 / P99、錯誤率;各層另有其特有指標:

| 層 | 特有量測項目 |
| --- | --- |
| 無鎖 | 超賣張數(問題的量化) |
| 悲觀鎖 | 鎖等待時間、連線池飽和點 |
| 樂觀鎖 | 重試次數分佈(不只平均值) |
| Redis 預扣 | Redis 扣減數與 DB 訂單數的對帳差額 |

### 3. 與前一層的對照

新的一層必須說明它相對前一層改善了什麼、代價是什麼。**只有數字沒有解讀的 spec 不算完成** —— 這個專案的產出是比較,不是四組獨立的數據。

## change 命名

`<動詞>-<目標>`,kebab-case。動詞用既有的這幾個,不要自創:
`add-`(新增能力)、`fix-`(修錯)、`refactor-`(不改行為的重整)、
`enforce-`(把既有規則變成會失敗的檢查)、`improve-`(既有能力的增強)。

封存後路徑為 `openspec/changes/archive/<YYYY-MM-DD>-<name>/`。

## tasks.md 的塊式切分

`##` 標題為一「塊」,切塊的唯一標準是**能不能獨立通過驗證鏈**,不是概念上像不像一組。有鏈式依賴的必須綁進同一塊,絕不留下編譯不過的中間狀態。

本專案的驗證鏈:

```bash
./mvnw compile          # 編譯
./mvnw spotless:check   # 格式
./mvnw test             # 單元測試 + ArchUnit guardrail
./mvnw verify           # 含 Testcontainers 整合測試
```

檔頭以引言區塊寫出該 change 的實際驗證鏈指令、「每塊綠燈後給 commit 指令由使用者執行」、以及塊與塊的依賴關係。

每個寫測試的塊結尾放**反向驗證**:刻意改壞 production code,確認測試真的變紅再改回來 —— 改不紅的是假測試。

## 寫作品質基準

格式規則決定「合不合法」,本節決定「有沒有用」。

### 動手寫之前先讀既有程式碼

寫 `design.md` 的 Context 之前先探索:這件事會碰到哪些既有實作、它們現在怎麼做、有沒有相關的守則。**探索時發現的東西就是 Context 該寫的內容。**

### 每個決定都要寫「不選 X 的理由」

`## Decisions` 的每一項都要有被否決的選項與否決的理由。**只寫結論等於把判斷過程丟掉** —— 下次有人想改回 X 時,無從得知當初為什麼不選。

代價要具體到可以反駁。「比較複雜」不算理由;「第 3 層的流程骨架與前三層本質不同,以繼承綁定會使骨架充斥 hook 與條件分支」才算。

### 驗收條件要可證偽

「併發控制有效」不是驗收條件,「1000 執行緒同時購買 500 張庫存,最終庫存為 0 且訂單總數為 500」才是 —— 後者可以寫成一條會失敗的測試,前者只能靠感覺。

每支 change 的 proposal 都該有一句話說清楚「怎樣算做完」,而那句話要能直接翻譯成測試。

### 壓測數據必須附測量條件

任何效能數字都要同時記錄:策略名稱、執行緒模型(平台 / 虛擬)、容器資源限制、`max_connections`、k6 的 VU 數與持續時間。

**沒有測量條件的數字不可比較,等於沒有數據。** 這是本專案特有的守則 —— 專案的核心產出是跨組比較,而比較的前提是條件一致。

### 範圍變化要留在文件裡,不要重寫歷史

實作途中追加的工作用 `2b` 這種編號插在相關塊之後,並交代它為什麼被併進來。

取消的項目用刪除線 + 粗體結論 + 理由,不要直接刪掉。

**任務清單與事實不符是最常見的失真來源。** 收尾時逐項核對,不要憑印象打勾。

### 反向驗證不是選配

每個寫測試的塊都要有:**刻意改壞 production code → 親眼看它變紅 → 還原 → 確認 `git status` 乾淨**。

改不紅的是假測試。這在本專案特別重要 —— 併發測試有時間性,一條寫錯的併發測試可能永遠是綠的(例如執行緒沒有真的同時啟動)。

### 不確定就留成 Open Questions,不要硬決定

`design.md` 的 `## Open Questions` 是給「知道有這個問題、但現在決定會是瞎猜」的事。硬做決定的代價是它會被當成已定案而擴散。

### 誠實勝過好看

- 做不到的事寫「做不到」與原因,不要寫成待辦
- 驗收沒過就說沒過,附上實際輸出,不要只寫「通過」
- 自己訂的判準後來發現不成立,就更正判準並說明為什麼
- **壓測數字不修飾。** 某層表現不如預期就照實記錄並分析原因 —— 那正是這個專案有價值的部分
